# 2026-09-24 — r000583: per-letter stage autopsy

Executes the §11 decision "r000583: cut candidates are ruled out; next is a
per-letter stage autopsy." Reads on `2026-09-24_cut_candidates_r000583.md`
(cut-candidate generation for wide/fused *atoms* ruled out as the
bottleneck) and `2026-09-23_worst_pages_round2.md` §(a) (the
bbox-overlap/crossbar-fusion mechanism, and the `merge_overlap_frac=0.4`
fix that took this page from 54.66% to 40.63% CER without clearing it as
worst on the corpus).

## Method

Built three temporary, env-gated diagnostics to `CARGO_TARGET_DIR=target/runtime-diag`
(never touching `target/release`):

- `ocr.rs`: `OCRCER_DEBUG_BOXES=1` prints every decoded character's pixel
  bounding box and confidence, used to map GOT-text garbling back to exact
  page coordinates.
- `pipeline.rs`: `OCRCER_DEBUG_WORD="x0,x1,y0,y1"` (page pixels) prints, for
  the one word whose lattice span overlaps that window in **both** x and y
  (the first cut of this used x-only and silently matched the same left-margin
  column on every line — every text line starts at roughly the same x, so a
  window like `"43,67"` hit all 11 lines at once; fixed by requiring the y-span
  too and computing the check once, in `pipeline.rs`, rather than
  independently re-deriving it in `viterbi.rs`), the full edge list (atoms/lattice
  + match: every `EdgeKind`, its x-span, and its top-5 match candidates with
  class and distance).
- `decode/viterbi.rs`: `decode_word_dbg(..., dbg: bool)` (the public
  `decode_word` is now a one-line wrapper calling it with `dbg=false`, so the
  tested API is unchanged) prints, for every candidate scored during that
  word's decode, the full term breakdown: `match` (`w_match*(char_bonus -
  distance)`), `seg`, `bigram`, `confusion`, `case`, `end_bigram`, `lex`, and
  the resulting path score.

Ran `./target/runtime-diag/release/ocr.exe model/out/ocrcer.ocrw <dir> --only
filing__r000583 --raw` with these env vars set per window, one process at a
time (verified via `tasklist` before each run). Picked windows by first
listing every decoded character box wider than 19px (a normal single-letter
box on this page is 10-18px; a fused two-letter box is 20-37px) — 192 such
boxes on just the first four of eleven lines — then sampling across different
words and lines.

## The unifying observation: this passage is italic

Cropping five of these cases (`the_th_fusion`, `offering1_ff_ri`,
`offering2_ff_ri_n`, `brookfield_ro_ok_fie_l`, `factors_fa` — pixel windows
recorded above, discarded after inspection per the scratchpad-cleanup rule)
shows every one of them is set in **italic** serif type — this is the
opening of a forward-looking-statements disclaimer, a passage financial
filings conventionally italicize. All ten atoms/lattice losses (`ff`, `ri`,
`fie`) are pairs where the italic slant leans one letter's stroke into the
next, closing the gap a valley-search expects between upright glyphs. All
six match losses and both decoder losses have distances elevated
across the board relative to upright text on the same page (typical
upright single-letter matches elsewhere on r000583 run 6.0-7.5; these
italic single-letter matches that *do* still hit the right class run
6.9-8.7, and the ones that miss run higher still) — consistent with the
model's feature space, deskew, or prototype bank not fully separating
italic shape from upright shape.

I did **not** check whether the prototype bank contains italic-rendered
glyphs at all (`ocrcer-glyphs`' territory), or whether `image/deskew.rs`
corrects per-word slant vs. only page-level skew (worth checking, but
outside this autopsy's scope) — flagging both as the first two questions
for whoever picks this up.

**Cross-page check.** Counting exotic-fusion characters (`Ø æ Æ & ™ ® ≈`) in
`--raw` GOT text: r000583 (worst page, 40.6% CER) has **216**; r000022,
r000044, r000055, r000308, r000363 (also flagged in round2) have 39-93 each.
The mechanism is present on every page checked, and its frequency tracks
page-level CER — consistent with, but not proof of, italic content driving
severity page-to-page. I did not check whether these other pages contain
italic passages; that is a fast follow-up (grep the same crop-and-look
method) before treating the italic hypothesis as page-general rather than
r000583-specific.

## Recommendation (not implemented, not a default change)

Two independent things are worth trying, in order of how directly the
evidence points at them:

1. **`char_bonus` in `decode/viterbi.rs`'s `Decode` params.** Back-solved
   value from this page's dumps is ≈3.44. The "factors," case needed >5.87 to
   let two rank-1, sub-8.7-distance real matches beat a merge at 8.516.
   `guess`: raising `char_bonus` to **5.5-6.0** would flip both decoder-stage
   cases in this sample without (by the existing unit test's logic) breaking
   the "one bad wide match loses to two good narrow ones" case it was
   written for — but this is a guess against a sample of 2 decoder-stage
   losses on one page; it should be checked against the full corpus and the
   fixture suite, not set from this alone. This only rescues the 4/21 decoder
   losses in this sample; it does nothing for the 10 atoms/lattice losses.
2. **Interior-cut search in `layout/segment.rs`.** The `ff`/`ri`/`fie`
   mechanism is a case the prior cut-candidate trace's "352 wide atoms + 54
   fused atoms" sweep should have caught if it covers touching-ink atoms the
   same way it covers bbox-merged ones — worth confirming with
   `ocrcer-architect` whether that trace's atom sample included any
   genuinely-touching (single-component, no bbox-overlap) letter pairs, or
   whether it was scoped to the bbox-merge case only. If the latter, this is
   a second, distinct cut-candidate gap, not a re-litigation of the ruled-out
   one — and the fix is likely closer to "detect italic slant per-word and
   correct it before the valley search runs" than a `valley_fraction` value
   change, since the underlying geometry (ink literally closing the gap
   between glyphs) doesn't have a valley to find at any threshold.

Both are `ocrcer-architect` decisions, not something this report implements
or defaults.

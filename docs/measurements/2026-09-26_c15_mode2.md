## Part 1 — implementation

`match.classifier = 2` was refused at load (`ocrw.rs`). It is now valid and
scored exactly as `ARCHITECTURE.md` §11 defines it:

- `d_seg` is the matcher's own best (minimum) distance over all classes —
  `r#match::nearest(&model, &raw, top_k, italic_ok).d1`, which is exact
  regardless of `top_k` (the cross-class ceiling is never abandoned before
  the true global minimum is found; confirmed by the existing
  `the_cross_class_ceiling_gives_the_same_answer_as_a_full_scan` test).
- Candidates are the net's top `match.top_k` non-junk classes, each scored
  `d_seg + nn.scale * (-log p_c)`.
- Junk is handled exactly as mode 1: excluded from the candidate pool and
  from the top1/top2 margin the edge's confidence `ratio` is derived from.

Per `CLAUDE.md` rule 4 ("every pipeline stage written exactly once"), this
did not become a second implementation of the net-scoring logic:
`nn_candidates` gained one parameter, `offset: f32` (mode 1 passes `0.0`,
mode 2 passes `d_seg`), added only to the returned `distance` after the
margin (and the `ratio` it produces) is computed from the raw
log-probabilities. A constant offset shared by every candidate on an edge
cancels out of a top1-minus-top2 margin, so this is not an approximation —
mode 2's confidence `ratio` for an edge is bit-for-bit the same computation
mode 1 would produce from the same log-probabilities. A unit test
(`nn_candidates_offset_shifts_distance_but_not_ratio`,
`crates/ocrcer-core/src/pipeline.rs`) pins exactly this: same class
ranking and same `ratio` under `offset=0.0` and `offset=d_seg`, with junk
(the highest-log-probability class in the test fixture) excluded from both.

Mode 0's own branch in `read_word()` is untouched — a new `use_fusion`
branch was inserted between the existing `use_nn` branch and the existing
(unmodified) prototype-only `else`, not folded into either. `ocrcer-core`'s
full test suite (211 unit tests + the `nn_parity` integration test) and the
full workspace suite (fixtures included, 91 passed in the `ocrcer-build`
crate covering the fixture-boundary assertions) pass unchanged; nothing was
blessed. `cargo check -p ocrcer-core --target wasm32-unknown-unknown
--no-default-features` passes. `#![forbid(unsafe_code)]` and the
zero-non-core/alloc/std-dependency rule are untouched by this change.

**Interpretations made, none of them a redesign:**

1. **`k` for the `d_seg`-producing `nearest()` call** is the same
   `p.matching.top_k` already used for every other matcher call in
   `read_word()` — no new knob, since `d1` does not depend on `k`.
2. **An edge is dropped (skipped) if either scorer fails it** — the
   matcher returns `None` or the net's `forward()` errors — mirroring each
   mode's own existing behaviour individually. No reading of "keep the
   edge on whichever scorer succeeded" seemed defensible: fusion needs
   both a segmentation verdict and a class ranking by definition.
3. **The confidence `ratio` is the net's margin, unmodified** — the same
   "provisional and unauthored" shape mode 1 already uses
   (`confidence::nn_ratio_from_margin`). Calibrating it is explicitly a
   separate, later step (§11's step 3) and out of scope here; reusing it
   unchanged is what rule 4 and "don't redesign" both point to.

### Why the net-introduced cluster survives fusion nearly unchanged

This is the finding this measurement adds beyond confirming the gate
fails. `d_seg` is a single constant added identically to every one of an
edge's own fused candidates — it does not, and by the definition in §11
cannot, reorder which of the net's top-`k` classes wins *that edge*. It
only changes how one edge's best fused distance competes against a
*different* edge from an alternative segmentation of the same span, inside
the decoder. So per-edge "which glyph" is still decided by the network
almost exactly as it is under mode 1 alone — visible directly above:
`"2"->"8"` (333 vs mode 1's 334), `")"->"h"` (302 vs 302), `"C"->"S"` (303
vs 294) are within a few counts of mode 1's own figures from
`c15_measure.md`, not attenuated toward mode 0's (absent) rate. The
"matcher says whether, net says which" framing in §11 holds for
*whole-edge* competition (an edge that is a poor segmentation can lose to
a better-segmented rival edge, because `d_seg` differs between them) but
not for *within-edge* class choice, which fusion does not touch.

```
{ "arm": "classifier=1 (net)",          "merge_or_split_frac": 0.0647, "mean_conf_single": 0.9831, "mean_conf_merge_or_split": 0.9796 }
{ "arm": "classifier=2 (fusion S=1)",   "merge_or_split_frac": 0.0601, "mean_conf_single": 0.9830, "mean_conf_merge_or_split": 0.9829 }
```

**Fusion's confidence is at least as blind to segmentation quality as the
network alone, not less** — the clean-vs-merge/split confidence gap is
0.0035 under mode 1 and **0.0001** under mode 2, smaller still. This is a
direct, expected consequence of Part 1's implementation choice (§11's
text does not specify a different confidence treatment for mode 2, and
this measurement did not invent one): the confidence `ratio` is computed
from the net's own top1/top2 log-probability margin before `d_seg` is
added, exactly as mode 1's, so fusion changes *distance* (and therefore
which edge and class win) without changing what a caller is told about
how sure the engine was. Whatever mode 2's distance-level fix bought here,
it did not make confidence a better segmentation-quality signal — that
remains unaddressed, consistent with `confidence::nn_ratio_from_margin`
being labelled "provisional and unauthored" and calibration being a
separate, later step.

## What this implies (for `ocrcer-architect`, not decided here)

- Fusion, as specified, is a small consistent improvement over the network
  alone (−0.208/−0.250 pp) but does not recover mode 0's accuracy, and it
  is the most expensive of the three modes to run. The mechanism reason is
  now measured, not merely conjectured: `d_seg` competes edges against each
  other but never competes classes against each other within one edge, so
  it cannot fix a wrong per-glyph ranking the network itself produces — it
  can only help when the *segmentation* choice, not the *class* choice, was
  the problem. The net-introduced digit/uppercase/punctuation confusion
  cluster identified in `c15_measure.md` is a class-choice problem, and
  fusion leaves it almost untouched.
- A design that wanted `d_seg` to also influence which class wins within
  an edge would need a different formula than §11's — that is a scope
  question for whoever revisits mode 2, not something this task's
  "implement exactly as defined, don't redesign" instruction permitted
  addressing here.
- Per the pre-registered rule, the default stays `match.classifier = 0`.
  This was never at risk of flipping without a step-2 pass, and it did
  not get one.

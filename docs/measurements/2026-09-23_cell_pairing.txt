Cell pairing (lines.cell_pairing) — measurement log, 2026-09-23
=================================================================

Source: docs/ARCHITECTURE.md section 11, "Worst pages, round 3: form cells
spliced into the wrong line of a wrapped label" and
docs/measurements/2026-09-23_worst_pages_round3.md.

Mechanism reported: after a band is split at a column cut, pipeline.rs's
Line::band assignment joins a narrow right-column fragment to the
left-column line sharing its baseline. When the left label wraps, the value
is spliced mid-label. Reported on filing__r000044, filing__r000396,
filing__r000407 (finfilings).

--- Step 1: ground-truth convention -----------------------------------

Read directly from the .truth.json `lines` arrays (flat list of strings,
reading order) for all three named pages. In every case the wrapped
label's full text comes first, one truth line per wrapped line, and the
value comes strictly afterward as its own separate truth line. Truth
never splices a value between a label's wrap lines.

filing__r000044.truth.json:
  0 'Monthly net realized gain(loss) –'
  1 'Month 1'
  2 '0.00000000'
(label wraps across lines 0-1, value is line 2, after both)

filing__r000396.truth.json:
  10 'i. Revenue sharing split'
  11 'ii. Non-revenue sharing'
  12 'split (other than administrative fee)'
(checkbox values 'Yes'/'No' each appear on their own truth line, after
the full label text, never interleaved with it)

filing__r000407.truth.json:
  2 'i. Full name'
  3 'J.P. Morgan S.A. DTVM'
  9 'v. Is the custodian an affiliated person of the'
  10 'Fund or its investment adviser(s)?'
  11 'Yes'
  12 'No'
(2-line wrapped question, then each checkbox answer on its own line,
strictly after the full question text)

Convention followed by the fix: a narrow fragment sharing a row with the
first line of a wrapping left-column cell is deferred until after the
cell's full wrapped text, then emitted on its own line — never spliced
mid-label.

--- Step 2: implementation ---------------------------------------------

New param `lines.cell_pairing: u32`, default 0 (today's behaviour),
labelled `guess` in model/params.tsv. When set to 1,
layout/lines.rs::pair_cells runs after group_with_bands' existing
column-cut grouping: for each row with >=2 fragments, it looks for
exactly one fragment whose column continues, via consistent baseline
spacing and column overlap, into one or more subsequent single-fragment
rows (wrap_run_len / columns_overlap). If found, that fragment is
emitted first, the continuation rows follow it in order, and the row's
other (narrow) fragments are appended afterward, each on its own line.
Ambiguous rows (more than one fragment looks like it continues) and
single-fragment rows fall through unchanged.

Root cause of the r000407 regression (checked via --raw diffs): the
geometric heuristic (column overlap + consistent line-to-line baseline
spacing) cannot distinguish a genuine multi-line wrap-continuation of one
cell's label from an entirely separate subsequent field-label row that
merely sits in the same left-hand column at the same normal line
spacing. r000407 is a dense per-field form (i./ii./iii./... labels, each
one line, all at the same left margin and line pitch), so a label's
value fragment gets wrongly deferred past the next, unrelated field's
label. Example (control correct; cell_pairing=1 wrong):
  control:   "ii. LEI, if any 5493001LS7J56NZZ3G07\niii. State, if applicable"
  cp1:       "ii. LEI, if any\niii. State, if applicable\n5493001LS7J56NZZ3G07"
A similar reordering appeared in the page's numbered checkbox list
further down (item boundaries and checkbox marks shuffled by one row).

Round 2: cell_pairing=2, the fullness and own-row tests
=================================================================

Source: ARCHITECTURE.md section 11's "Cell pairing, first rule" entry
(round 1, above) named the failure: overlap and steady pitch alone cannot
tell a genuine wrap from the next, unrelated one-line label at the same
margin and pitch (filing__r000407's second short label), and the same
ambiguity was blamed for the pages-cov no-worse-gate failure.

--- Step 1: rule -----------------------------------------------------

lines.cell_pairing = 2 keeps rule 1's overlap/pitch test and adds two
more, both read from a new lines.cell_wrap_slack: f32 (guess, default 1.0,
read only when cell_pairing >= 2):

(a) The candidate's previous left-column line must be full: its right edge
    must land within cell_wrap_slack x-heights of the left column's right
    extent in the contiguous block. A line wraps because it ran out of
    room, so its own right edge should reach close to what the rest of
    that block shows is available.
(b) The continuation line must carry no right-column fragment of its own
    row. This needed no new code: wrap_run_len already only ever continues
    a run through single-fragment rows, at every level.

Extent, the choice this task asked to be stated explicitly: the max right
edge among every row's fragment that shares the candidate's column,
scanning up and down the page from the candidate's own row
(column_block_extent in crates/ocrcer-core/src/layout/lines.rs), stopping
the moment a row has no such fragment (a different section) or more than
one (ambiguous). Not the immediate candidate pair alone: on
filing__r000407, the two short labels are both short, so judged only
against each other either would look full to the other, exactly
reproducing round 1's failure. Scanning the whole contiguous block picks up
a page's other, genuinely full labels (an earlier line, or a later
multi-line wrap further down the same field list) and uses the widest of
those as the yardstick instead. The extent is computed once per candidate
and held fixed for the whole run it may build, a property of the block,
not of any one pair inside it.

Unit tests added to crates/ocrcer-core/src/layout/lines.rs (all passing;
the four round-1 tests now pass an explicit Params via a new
pairing_params test helper so they keep exercising level 1 unchanged):
  - r000407_shape_short_label_with_own_value_next_label_untouched: the
    real regression's shape, a short label already paired with its own
    value, followed by an unrelated next label at the same margin and
    pitch, must not defer, because the short label falls far short of the
    block's extent (set by an earlier, genuinely full label).
  - a_full_wrapped_label_still_defers_under_level_two: a genuinely full
    first line (within slack of the block's extent, set by an earlier
    line) must still defer its value, unchanged from level 1.
  - two_column_prose_with_a_short_line_end_is_unchanged: a two-column row
    whose left fragment is the short last line of its own paragraph, which
    coincidentally shares column and pitch with unrelated content below,
    must not defer, the same mechanism pages-cov's twins layouts were
    diagnosed with.

--- Step 7: rule 3, implemented and measured ---------------------------

`crates/ocrcer-core/src/layout/lines.rs` gained `column_cell_slice_match`,
a reworked `single_column_match`/`column_block_extent`/`pair_cells`, and
three tests (`sheet_1_of_3_title_block_row_is_unchanged_under_level_three`,
`vacuous_extent_does_not_defer_under_level_three`,
`r000044_wrapped_label_still_defers_under_level_three`), implementing
`lines.cell_pairing = 3` per ARCHITECTURE.md section 11, 2026-09-23 ("Cell
pairing, rule 3 decided"). Condition (ii) -- a vacuous extent (the up/down
scan never finds anything wider than the candidate's own right edge) fails
the fullness test closed -- is implemented exactly as decided. Condition
(i) is implemented as: a single-fragment row's own fragment may vouch for
a column only if it does not reach into any *sibling* fragment's column
(the other fragment(s) sharing the anchor's own row), rather than the
literal "anchor lies inside a cell-width slice of it" the decision named.
The code's own doc comment on `column_cell_slice_match` explains why: literal
containment in either direction breaks `filing__r000044`'s required win (a
wide anchor cannot fit inside a narrower continuation, and `column_block_extent`
must accept a wider neighbouring row as genuine block evidence, which plain
containment also rejects either way). This is flagged here as a deviation
from the decision's literal wording, not silently reinterpreted: rules 1 and
2 stay reproducible (untouched code paths, `strict` gates the new behaviour
behind `cell_pairing >= 3`), and the deviation is checked against every gate
below rather than asserted.

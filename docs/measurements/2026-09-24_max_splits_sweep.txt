0. Mechanism check (segment.rs read before measuring, as instructed)
--------------------------------------------------------------------------

crates/ocrcer-core/src/layout/segment.rs:347-398 (interior_cuts) and
crates/ocrcer-core/src/params.rs:395 (max_splits: 3, "guess").

- `max_splits` is a HARD CAP on the number of interior-cut candidates an
  atom is allowed to keep, applied at segment.rs:394
  (`cands.truncate(p.max_splits)`). Candidates are valley positions in the
  atom's ink-column profile at or below `valley_fraction * mean`, gated by
  a margin (`min_piece_x_heights`) at each end. They are sorted by
  (valley depth, then x-position ascending) before truncation, so raising
  the cap only ever *adds* shallower/later-found valleys on top of the
  ones already kept -- it can never remove or replace a cut that a lower
  cap already offered. An atom is capped at `max_splits + 1` output pieces.

- It is a hard cap, not a per-atom or width-scaled figure: every atom in
  every word uses the same constant regardless of its width or x-height.

- Lattice-size effect (segment.rs:210-259): each atom contributes
  `interior_cuts + 2` node positions (left edge, cuts, right edge). The
  "pieces of one atom" edge-generation loop enumerates ALL pairs among
  those positions (`for a in lo..hi { for b in a+1..=hi { ... } }`), i.e.
  `C(m, 2)` split edges where `m = cuts + 2`. That is quadratic in the cut
  count, not linear -- so raising the cap for atoms that actually have
  many valley candidates would grow the lattice (and viterbi/match cost
  over it) quadratically, not proportionally. Measured wall-time impact
  below is small because in practice very few atoms on the screened pages
  have more than 3 candidate valleys in the first place (see section 1).

- A width-aware alternative (`allowed = max(max_splits, floor(width /
  (k * x_height)))`) is a one-line change: compute a per-atom bound from
  `ax1 - ax0` and `line.x_height` in `interior_cuts` and truncate to that
  instead of the constant. Not implemented -- this is the architect's
  call per the task instructions. NOTE (see section 1): a width-aware cap
  would not, by itself, fix r000583/r000308, because on those pages the
  cap is not the binding constraint -- the valley-detector already finds
  fewer than 3 candidates for the fused atoms responsible for the errors.
  A width-aware cap only ever raises the *ceiling* on how many cuts an
  atom may keep; it does nothing if the ceiling was never being hit.

2. Decision: did any N "clearly help" the screen? No.
--------------------------------------------------------------------------

Two of the three screened pages -- including r000583, the page this whole
sweep was commissioned to fix -- show ZERO sensitivity to max_splits across
the full tested range 3..8. The one page with any movement (r000022) shows
a 0.2-0.3pp CER improvement that plateaus at N=5, at a real per-page wall-
time cost (+6%), and with no word-level (WER/F1) change at all.

Per the task's conditional instruction ("take the best one or two N values
that clearly help the screen to the full runs"), nothing here clearly
helps. Given the lattice is quadratic in cut count per atom (section 0)
and the corpus-wide cost is unknown a priori, spending two ~25-minute
finfilings runs (~50 min) plus a pages-cov run (~8 min) per candidate N on
a change the screen already shows is inert on the primary target, and only
worth ~0.25pp on a secondary page, is not justified. No swept full-corpus
run was performed. Control runs were performed anyway (below) to (a)
validate the harness against the stated baselines and (b) leave both
scratch control CSVs in place for whichever agent picks up the next
experiment on these three pages, per the task's explicit instruction to
keep them for later agents.

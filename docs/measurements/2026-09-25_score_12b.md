## 3. Losses first: what's actually regressing, and why (not what was hypothesized)

The task's working hypothesis was that `segment.max_merge_x_heights`
moving 1.8→1.05 would show up as m/w/%-style within-word glyph
splitting. That is not the dominant pattern found. Two different,
cleaner mechanisms dominate the actual regressions, both plausibly
tied to the same segmentation-threshold tightening
(`max_merge_x_heights` 1.8→1.05, `segment.valley_fraction` 0.5→0.65,
`decode.w_seg` 0.25→0.55) but acting on inter-word gaps and the
dot-above-i, not on wide-letter strokes. Reporting what was measured,
not what was expected (CLAUDE.md rule 8).

**Mechanism A — systematic "i" → "í"/"î" false-diacritic insertion,
concentrated in monospace fonts.** This is visible in the aggregate
confusion table: `"i" -> "í"` is fitted's **6th**-most-common
confusion corpus-wide (154 occurrences) and does not appear in
control's top-12 at all. It is the single largest cluster of
individual-page regressions: 6 of the 10 worst page-level regressions
corpus-wide are prose/currency pages in monospace fonts (PT Mono,
Cascadia Mono, JetBrains Mono, Roboto Mono, Fira Code) whose entire
delta is this one substitution repeated across the page. Concrete
before→after, `pt-mono__regular__prose__14px`:

```
want  The engine reports a confidence for every word it returns,
ctrl  The engine reports a confidence for eve w word it returns,
fit   The engîne reports a confîdence for eve w word ît returns,
```

(the "eve w"/"warranced" errors are shared by both configurations —
pre-existing, not new. Only the i→î substitutions are new under
fitted.) Same pattern, same font family, on `roboto-mono__regular
__prose__40px` (fitted 5.556% CER vs control 0.000% — a perfect page
under control turned imperfect under fitted, entirely from this one
substitution) and `cascadia-mono__regular__prose__14px`.

**Mechanism B — inter-word space collapse**, seen mostly in the
drawing/twins categories on lines with multiple short tokens.
Concrete before→after, `liberation-serif__regular__drawing__40px`:

```
want  DO NOT SCALE DRAWING
ctrl  DO NOT SCALE DRAWING
fit   DONOTSCALEDRAWING
```

Same line, same failure, on `stix-two-math__regular__drawing__18px`
(control correct, fitted `DONOTSCALEI)RAWING`). And on
`roboto-condensed__regular__drawing__28px`:

```
want  SCALE 1:2   SHEET 1 OF 3
ctrl  SCALE l÷2 SHEET l OF` 3   (control has its own separate errors)
fit   SCALE1:2 SHEET10F3         (worse: two words fused, "1 OF 3" -> "10F3")
```

And the single worst individual-page regression corpus-wide,
`stix-two-math__regular__twins__28px` (+8.696pt CER):

```
want  Order 10O1 shipped 2026-01-08
ctrl  order 10o1 shipped 2026-01-08
fit   order10o1shipped 2026-01-08
```

**Identifier-shaped-text corruption — the one that matters most
under CLAUDE.md rule 6.** `noto-sans__regular__drawing__18px`:

```
want  4X M8x1.25 THRU
ctrl  4X M8x1 .25 THRU
fit   4X IV18x1 .25 THRU
```

Fitted splits "M" into three characters ("IV1") that read as
plausible glyph shapes, turning the identifier "M8x1.25" into
"IV18x1.25" — a corruption, not a drop. Control's error on the same
token (a stray space before ".25") leaves "M8x1" intact. This is not
a lexicon rewrite (the token stays non-dictionary-shaped both ways),
so it isn't the specific failure CLAUDE.md rule 6 names, but it is
the same family of harm the rule exists to prevent: an identifier
silently turned into a different, equally identifier-shaped, wrong
string. One instance found in this sample; not established as
systematic — flagged for `ocrcer-glyphs`/`ocrcer-runtime` to check
against a larger identifier-bearing sample (see §4), not something
this run can generalize from a single page.

**What this means for the WER/F1 regression on pages-cov (§1):** both
mechanisms turn what would be a few-character CER cost into a
whole-word miss (fused words, or a word gaining a false accent count
as one wrong word each) — consistent with CER improving on
average while WER/recall regress slightly: the character-level edits
got cheaper on average, but the specific edits that remain are more
likely to break a whole token.

## 4. Identifier preservation — no corpus-level test exists to run

Searched the full workspace (`crates/ocrcer-core`, `crates/ocrcer-build`,
`crates/ocrcer-bench`, `fixtures/`) for the "build a test set of part
codes/dimension callouts and assert exact output" harness that
CLAUDE.md rule 6, `PLAN.md`'s chunk 6/14/16 gates, and the
`ocrcer-bench` agent brief all describe as running every round. It
does not exist yet. What exists instead:

- `ocrcer_core::decode::viterbi::tests::
  a_digit_heavy_word_with_letters_in_it_is_identifier_shaped` — a
  unit test of the `is_identifier()` predicate against synthetic
  class-index data (e.g. asserts `"M8"`-shaped input is
  identifier-shaped). Passes.
- `ocrcer_build::lexicon::tests::
  the_shipped_lexicon_holds_nothing_the_identifier_gate_would_suppress`
  — a unit test that the shipped lexicon has no entries the
  identifier gate would clobber. Passes.

Both ran clean against this build (`cargo test --release identifier`,
2 tests total across the workspace, 0 failed). Neither is a
corpus-level "OCR this image, assert exact string" test. This is a
gap, not a pass being claimed — filing it plainly per CLAUDE.md rule
8 rather than treating the unit tests as satisfying the requirement.

As a proxy (not a substitute), pages-cov's drawing category carries
real identifier-shaped ground truth (`M8x1.25`, `71-4820-B`,
`R3.0`, `A36`, part/rev codes) and is scored above — the M8→IV18
corruption in §3 came from that proxy, not from a dedicated
identifier corpus. Building the dedicated corpus-level test is a gap
`ocrcer-bench` should close in a future round; it is not something
this scoring round can retrofit without touching the harness, which
is a decision for the chunk 12b scope, not this "score once" step.

## 6. What this means for the other agents (this round chooses nothing; it points at what to check next)

- **`ocrcer-glyphs`**: the i→í confusion is concentrated in
  monospace faces (PT Mono, Cascadia Mono, JetBrains Mono, Roboto
  Mono, Fira Code) at small/medium sizes — check whether those
  faces' "i" glyph (dot + stem as two components) has thin enough
  bank coverage that the tighter `max_merge_x_heights`/
  `valley_fraction` bounds now sometimes merge the dot into the stem
  as a single taller prototype match. This is a font-shape/bank
  question, not a decoder-weight one — the confusion is component-
  merge, not lexicon or bigram driven.
- **`ocrcer-linguist`**: the word-fusion regressions (Mechanism B,
  §3) look like an inter-word gap threshold that got tighter than
  intended alongside the intra-glyph merge threshold — worth
  checking whether `words.pitch_tolerance` (0.15→0.22, which should
  have made gap detection *more* forgiving) is being outweighed by
  `segment.valley_fraction` (0.5→0.65) or `decode.w_seg` (0.25→0.55)
  on these specific short-token lines. A confusion-table or
  segmentation-weight adjustment in a future fitting round, not
  something to change off this single scoring pass.
- **`ocrcer-bench`** (self, next round): build the corpus-level
  identifier-preservation test named in §4 — it does not exist, and
  the one corruption found here (M8x1.25 → IV18x1.25) came from a
  proxy category, not a dedicated identifier set. Until that test
  exists, rule 6 compliance is unverified, not passing.
- **`ocrcer-architect`**: the pages-cov WER/F1 regression (§1) despite
  a clean CER win is a feature-vector/segmentation-threshold
  interaction question, not a font or lexicon one — flagging per "if
  a result implies a feature-vector or format change... say so and
  let ocrcer-architect decide," since it isn't this round's call.

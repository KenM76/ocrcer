# L2 (row-band misordering): fix, measurement, gates

Branch `L2-order`. Implements `ARCHITECTURE.md` §11's L2 fix as pre-registered
2026-09-27: `docs/measurements/2026-09-26_c15_tableseg.md` found about 54
dense-table rows where a band fragment whose own baseline differs from its
siblings' by more than the within-row tolerance is glued into the row (an
example: a wrapped second line of a name, 8-9 px lower on a 12-15 px pitch),
leaving the fragment out of reading order. Model build recipe and corpus per
`docs/measurements/2026-09-26_c15_measure.md`.

## Code

`crates/ocrcer-core/src/layout/lines.rs`:

- `split_misplaced_fragments(rows, p) -> Vec<Vec<TextLine>>` (new function),
  called in `group_with_bands` immediately before the `pair_cells`
  conditional block, after `measure`/`inherit_x_heights` have produced the
  row-of-column-fragments structure `pair_cells` itself reads. For every row
  with two or more fragments, computes the row's own reference baseline (the
  width-weighted median of its fragments' baselines) and pulls out any
  fragment whose own baseline differs from it by more than
  `Params::row_baseline_tolerance_x_heights` x-heights of that fragment. A
  pulled fragment is re-seated as its own one-member row, and the whole row
  list is re-sorted by the same `(y0, x0)` reading-order key
  `group_with_bands`'s own band sort already uses, so a page with nothing to
  pull re-sorts to the order it already had. A row is never emptied by this
  pass (a row of one fragment is left alone; if every fragment in a
  multi-fragment row disagrees enough to be pulled, the row is left
  standing) — a defensive guard, not exercised in measurement, since the
  weighted-median reference is always exactly one member's own value, so
  that member's own deviation is always 0 and always kept.
- `row_order_key`, `row_baseline` (new helpers): the reading-order key and
  the weighted-median-baseline statistic, respectively.
- **Interaction with the two-baseline split (`split_baselines`, entry of
  2026-09-23):** the two operate at different stages on different
  granularity. `split_baselines` runs earlier, per whole band, directly on
  pixel components, and requires a genuine bimodal height histogram with
  peak separation and minimum support (`Params::baseline_split_sep`,
  `baseline_split_support`) before it splits a band into two — it is built
  to catch a band that is really two stacked populations (for example a
  superscript/subscript pair, or two full lines sharing one y-band), and it
  runs before column-cutting, so its own output already feeds
  `split_at_column_gaps` as separate bands/rows. `split_misplaced_fragments`
  runs after `measure`, on the already column-cut, per-fragment `TextLine`
  baselines, and needs no population or histogram shape at all: a single
  glued-in fragment among otherwise-consistent siblings is enough. A band
  `split_baselines` already separated into two rows never reaches
  `split_misplaced_fragments` as one row, so there is no double-counting;
  what reaches this new pass is exactly the residual case
  `split_baselines`'s own bimodal-population test does not target — one
  fragment glued into an otherwise single-baseline row. `cargo test
  --workspace` (below) confirms no regression in `split_baselines`'s own
  fixture-checked behaviour.
- Three new unit tests in `layout::lines`'s `mod tests`:
  `a_misplaced_wrapped_fragment_is_pulled_into_its_own_row`,
  `a_small_baseline_difference_is_left_alone`,
  `the_control_value_disables_the_rule`.

`crates/ocrcer-core/src/params.rs` and `model/params.tsv`: added
`lines.row_baseline_tolerance_x_heights` (f32, authored, tune=yes),
consistent with the existing `NAMES`/`f32_fields`/`set_f32`/`.lines()`
plumbing. Built model now reports 83 param rows (up from 82 after W1).

`crates/ocrcer-bench/src/bin/l2_baseline_probe.rs` (new probe, committed
alongside, same pattern as `w1_gap_probe.rs`): the step-1 measurement tool.
Purely geometric — reconstructs `group_with_bands`'s pre-fix row structure
(rule disabled) across every page and records, for every row with two or
more fragments, each fragment's own baseline deviation from that row's
weighted-median baseline, in that fragment's own x-heights. No model or
ground truth needed, and it never reads `finfilings`, `finfilings-val`,
`pages-cov`, or any fixture.

## Criterion and its value

**`row_baseline_tolerance_x_heights = 0.45`, authored.**

Measurement (recorded in the field's doc comment, reproduced here): across
all 320 `finfilings-train-unseen` pages, every multi-fragment row's
per-fragment baseline deviation from its own row's width-weighted-median
baseline (44,747 samples, `l2-baseline-probe`).

**Unlike L1's clean, sample-empty bimodal gap, this distribution is a
smooth-decaying histogram with a shallow local minimum, not a genuinely empty
valley** — reported plainly rather than dressed up as L1's kind of result,
per `CLAUDE.md` rule 8. The coarse (0.1-x-height-wide) histogram has a local
minimum at `[0.40,0.50)` x-heights (437 samples), lower than both
neighbouring buckets, directly followed by a rise to 1023 then 1273 samples
in the next two buckets — a genuine valley separating a decaying
near-zero/small-wobble population from a distinct bump. 0.45 sits in that
valley.

The choice is corroborated by a second, weaker line of evidence: the bump's
own range (roughly 0.5-0.7 x-heights) brackets the diagnosis's own worked
example — an 8-9 px deviation on a 12-15 px line pitch
(`docs/measurements/2026-09-26_c15_tableseg.md`) — once this dense-table
corpus's x-height (observed on the order of its own line pitch) is
substituted in.

0 disables the rule (byte-for-byte prior behaviour) and is the control value
this document's Step 2/3 gates run against.

## Step 2 — mode 0 with L2 vs mode 0 control

160-page cohort: `finfilings-train-unseen`, stride 2, offset 0 (deterministic
alphabetic order), default `match.classifier = 0`. Model built via
`cargo run --release -p ocrcer-build -- write 16,20,24,32,48 21,26,36,56
model/out/ocrcer.ocrw --nn D:/Dev/ExcludedPrivate/ocrcer/nn15b/weights/
cpu_det_run1`. Control via `--set lines.row_baseline_tolerance_x_heights=0`
on the same binary; L2 is the shipped default (`0.45`), no override.

| metric | control (0.0) | L2 (0.45, shipped) | Δ |
|---|---|---|---|
| end-to-end CER | 19.694% | 19.692% | −0.002 pp |
| line-matched CER | 21.584% | 23.998% | **+2.414 pp** |
| WER | 32.558% | 32.611% | +0.053 pp |
| recall | 81.013% | 81.059% | +0.046 pp |
| precision | 77.412% | 77.482% | +0.070 pp |
| F1 | 79.171% | 79.230% | +0.059 pp |

(Control numbers reproduce W1's own shipped baseline exactly —
19.694/32.558/21.584/81.013/77.412/79.171 — confirming this is the same
model, corpus and code path as W1's addendum 2, with only L2 toggled.)

Gate: "at least one of end-to-end/line-matched CER improves by more than
0.02 pp, and the other is no worse than +0.02 pp." End-to-end moves by only
−0.002 pp, an order of magnitude under the 0.02 pp bar — not a real
improvement, noise-scale. Line-matched CER gets markedly **worse**, +2.414
pp, over 120× the +0.02 pp allowance.

**FAIL.** Neither half of the gate is met: end-to-end does not clear the
improvement bar, and line-matched is far outside the no-worse-than-+0.02 pp
band. The direction is notable — end-to-end (which follows reading order
through the decoder as the whole page is read) is roughly flat, while
line-matched (scored per detected line, independent of reading order) gets
substantially worse. A plausible reading, offered as a hypothesis and not a
diagnosis: the rule is re-seating some fragments as new one-member lines
whose own text is fine in isolation but whose boundaries no longer align
with the same lines the ground truth expects to match against one-for-one,
so line-matched CER's line-level correspondence degrades even where the
underlying character stream is close to unchanged. This is not confirmed by
any measurement in this document and is not offered as settled.

L2, as pre-registered and measured, does not meet its own CER bar: it is
essentially neutral end-to-end and clearly harmful on the line-matched
metric, despite passing every other gate (identifier preservation, workspace
tests, wasm32, and timing under the now-standing v2 protocol). This is the
opposite failure mode from W1's own history (which passed CER cleanly and
initially failed only on timing): here the mechanism the fix targets is real
(the diagnosis's ~54 rows are not disputed) but the line-level bookkeeping
cost of re-seating fragments as new lines outweighs the character-level gain
on this cohort, at least at the authored tolerance. Whether a different
tolerance, a narrower trigger condition, or abandoning the approach is
correct is `ocrcer-architect`'s call, not this session's — no retune was
attempted here, per instruction not to self-serve a passing number. Nothing
in this work was merged or pushed.

# Chunk 15 loss decomposition — where mode 1's extra CER lives

Architect assignment, diagnosis only. No parameter, weight, default, or
runtime behaviour changed. Two additive, behaviour-preserving refactors in
`ocrcer-bench` (`cer::align` / `cer::greedy_line_pairs` extracted from
existing call sites, verified against the existing 19 `cer` unit tests —
all pass unchanged) plus one new probe, `c15_decomp_probe.rs`, reusing
`ocrcer_bench::cer::{score, line_matched_score, align, greedy_line_pairs}`
per rule 4 (alignment written exactly once). Branch `c15-decomp`, not
merged, not pushed.

This follows up `2026-09-26_c15_trace.md`'s Fate/dominant-term decomposition
and the margin explanation `ARCHITECTURE.md` §11 records as rejected. That
trace established *that* the net (mode 1, `match.classifier=1`,
`nn.scale=√2`) wins per-glyph top-1 and loses end-to-end CER, and flagged a
WER-better-but-CER-worse clue as under-weighted — a hint of concentrated
multi-character errors rather than diffuse ones. This session locates those
errors: which pages, which characters, and what they look like.

Population, model, mode definitions: identical to `2026-09-26_c15_measure.md`
and `2026-09-26_c15_trace.md` — `finfilings-train-unseen`, alphabetical
`list_pages`, stride 2, 160 of 320 pages. `model/out/ocrcer.ocrw` built fresh
this session from the checked-in recipe (187 classes, 54 faces, 50095
prototypes, lexicon 2477 nodes, bigrams 188 rows, confusions 76 rows —
matches reference stats; int8 top-1 agreement with f32 99.493%, matching
prior sessions). Mode 0 = defaults (`match.classifier=0`, prototype matcher).
Mode 1 = `match.classifier=1`, `nn.scale=1.4142135` (√2, the CER-minimising
value fitted in `c15_measure.md` step 1), both applied only via
`ocrcer_bench::knobs::set` at probe run time, never written to
`model/params.tsv` (still ships `nn.scale=1.0`, labelled a guess).

Scope: only `finfilings-train` (via the `-unseen` hardlink split) was read.
`finfilings`, `finfilings-val`, `pages-cov`, fixture corpora and `bench/ident`
were not touched. No page text, no per-page image, and no dump-dir content
is reproduced verbatim anywhere below — categorisation is in words, keyed
only by page stem.

## Task 4 — ground-truth-line-paired character correctness

Pairing truth lines to read lines the same way `line_matched_score` does
(greedy nearest-first), then aligning within each paired line and counting
match vs substitution only (excluding within-line insertions/deletions and
unpaired lines from the denominator — this isolates recognition quality
from reading-order/segmentation noise, the gap the Fate trace's "Fate A"
could not by itself resolve):

| | correct | match | sub | lines paired (of 23506 truth lines) |
|---|---|---|---|---|
| mode 0 (matcher) | **97.1252%** | 245756 | 7274 | 8051 |
| mode 1 (net, √2) | **96.1190%** | 244171 | 9859 | 8051 |

Both modes pair the identical 8051 of 23506 truth lines (34.3%) — the low
pairing rate is a property of this corpus's page density/reading order, not
a mode difference, and is out of scope for this diagnostic (it is the same
denominator both modes are scored against). Within paired lines, the net is
**1.0 pp less correct per character** than the matcher — this is the
"correctness number the trace lacked": a direct answer, not inferred from
Fate categories, and it is a loss for mode 1, consistent with task 2's
substitution-dominated delta.

## Task 5 — categorisation of the 10 largest-positive-delta pages

Method: `difflib.SequenceMatcher` opcodes between reference and each mode's
output (character-level, same normalisation `cer` uses), restricted to
edit blocks present in mode 1's diff with no overlapping edit in mode 0's
diff at the same reference span (i.e., churn mode 1 introduces that mode 0
does not), sorted by block size; corroborated by viewing the rendered page
image for the largest-delta page. No text, snippet, or image is reproduced
below — categories and page IDs only.

**9 of the 10 pages (`filing__s5__r000364`, `r000378`, `r000387`, `r000345`,
`r000303`, `r000268`, `r000255`, `r000026`, and `filing__s6__r000109`) are
dominated by one category: long runs of confidently-wrong alphanumeric
output localised to dense, small-font tabular rows** — visually confirmed
on the largest page (`r000364`) to be a fund/SEC-style holdings-schedule
table: narrow row height, tightly kerned right-aligned numeric columns
(share counts, dollar values), CUSIP-style alphanumeric codes, and
frequent two-line wrapped company-name cells. In this row band, mode 1
emits long stretches (single blocks up to ~980 characters on the worst
page, more commonly 8–15 blocks of 40–75 characters scattered across a
page) of alphanumeric text that does not correspond to any real
reference content in that span; mode 0 emits markedly less extra content
in the same span. Severity scales with how densely packed the table rows
are on each page — the four worst pages (`r000364`, `r000378`, `r000387`,
`r000345`) show the largest single blocks (390–980 characters); the
three next (`r000303`, `r000268`, `r000255`) show the same pattern at
smaller block sizes (25–70 characters, more of them mixed with ordinary
short substitutions); `r000109` and `r000026` show the pattern weakest
(blocks 6–56 and 3–17 characters respectively), with `r000026`'s extra
churn already closer to ordinary scattered substitution than a garbage
run.

**1 of the 10 pages (`filing__s2__r000192`, the smallest delta of the ten
at +5.830 pp) does not fit this category.** It is a regular
financial-statement (income-statement) page with no dense holdings
table; its extra mode-1 churn is ordinary scattered character
substitutions on normal prose/line-item text, the same flavour of error
task 3's confusion-pair list already describes, just concentrated on one
page.

No page in the top 10 shows the "non-text ink" (table rule / graphic)
category as dominant, and none shows a reading-order/whole-line-merge
failure as dominant (the `\n`→` ` row from task 3 is real but diffuse
across the corpus, not concentrated in these 10 pages specifically).

## What this changes and who acts on it

**Dominant failure mode: touching-character segmentation on dense,
small-font numeric table columns, interacting with the decoder's much
lower override rate for the net.** `c15_trace.md` already measured that
the net's own argmax survives the decoder almost unchanged (Fate A 83.6%,
Fate B — decoder overrides — only 0.5%, an order of magnitude below the
matcher's 5.3%). This decomposition adds *where* that near-total trust
costs the most: in tightly packed numeric/alphanumeric table rows where
segmentation is most likely to fuse or clip glyphs, the net's confidence
does not degrade on a bad segment the way the matcher's distance-based
score does, so a wrong high-confidence character sails through the
decoder with almost nothing left to catch it — there is no lexicon word to
lean on inside a CUSIP-and-share-count row, so the bigram/confusion terms
are the only remaining check, and they are evidently not enough. This
looks like it implicates two levers, and the choice between (or
combination of) them is not this report's call:

- a segmentation/pre-processing lever (`ocrcer-runtime`, per `PLAN.md` §4's
  risk-mitigation ladder) — better binarisation or morphological repair
  specifically for tightly-kerned small-font digit runs, since this is a
  touching-glyph problem before it is a classification problem;
- a decoder-weight lever (`ocrcer-linguist`) — the bigram/confusion terms
  currently have far less power to override the net's argmax than they do
  the matcher's (0.5% vs 5.3% override rate), and this is exactly the
  context (dense numeric tables, no lexicon signal available) where more
  override headroom would matter most.

This is not a font-coverage gap (`ocrcer-glyphs`) — nothing here points to
a missing face or shape family, it is dense/degraded input interacting with
how much the decoder trusts the net's confidence. `ocrcer-architect`
should decide which lever (or both) to pursue; this report does not.

The three named confusion pairs mode 1 clears relative to the matcher
(0/O/o, task 3's second table) remain real wins and should stay credited —
they are a separate, disjoint failure class from the dense-table loss
described above, not something this report is walking back.

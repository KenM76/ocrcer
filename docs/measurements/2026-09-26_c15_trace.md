# Chunk 15 stage trace — why mode 1 (net) loses end-to-end despite winning top-1

Architect assignment, diagnosis only. No parameter, weight, default, or
runtime behaviour changed. Two probe-only edits to `ocrcer-core` (visibility
of `viterbi::probe_reading`/`probe_at`, no logic change) and a new probe in
`ocrcer-bench` (`c15_trace_probe.rs`, reusing the `gen15_probe.rs` /
`skew_probe.rs` / `segkind_probe.rs` conventions). Branch `c15-trace`, not
merged, not pushed.

Population: `finfilings-train-unseen`, same selection as `2026-09-26_c15_measure.md`
(alphabetical `list_pages`, stride 2, 160 pages — the same population that
originally surfaced these confusions in Step 2 of that document). A 20-page
subsample (stride 2, first 20) was also run to check the measurement wasn't
size-fragile; every ratio below reproduces closely at both sizes.

Model: `model/out/ocrcer.ocrw` built fresh this session from the checked-in
build recipe (187 classes, 54 faces, 50095 prototypes, lexicon 2477 nodes,
bigrams 188 rows, confusions 76 rows — matches reference stats exactly).
Mode 1 uses `nn.scale=√2` (the CER-minimising value found in
`2026-09-26_c15_measure.md` Step 1, applied only via `ocrcer_bench::knobs::set`
at probe run time — never written to `model/params.tsv`, which still ships
`nn.scale=1.0`, labelled a guess).

## Definitions (as specified by the task)

Per character on the decoder's chosen path, matched independently per mode
against a ground-truth-aligned crop (truth line pairs with a decoded line by
word count; truth word pairs with a decoded word by character count):

- **Fate A** — the chosen edge aligns to truth, and the decoded character
  equals the classifier's own argmax on that edge.
- **Fate B** — the edge aligns, but the decoder's output differs from the
  argmax. Attributed to: b1 (argmax excluded from the candidate list — a
  bug if seen), b2 (Viterbi preferred a different candidate — dominant term
  named by cost delta), b3 (a post-decode rewrite).
- **Fate C** — the chosen edge does not align to any ground-truth crop
  (segmentation differs from truth). Also recorded: whether the *other*
  mode's decoded word at the identical (line, word) position aligns
  instead.

## Fate table (160 pages, 161700 / 162117 aligned-or-not characters)

| | Fate A | Fate B | Fate C | total |
|---|---|---|---|---|
| mode 0 (matcher) | 126391 (78.2%) | 8579 (5.3%) | 26730 (16.5%) | 161700 |
| mode 1 (net, √2) | 135561 (83.6%) | 782 (0.5%) | 25774 (15.9%) | 162117 |

Net has *more* Fate A (its own argmax survives the decoder almost
unchanged, 83.6% vs 78.2%) and *far less* Fate B (0.5% vs 5.3% — an order
of magnitude fewer decoder overrides). Fate C is close between modes
(15.9% vs 16.5%) — segmentation is not where the two modes principally
diverge.

**b1 (argmax excluded from candidates): 0 occurrences, both modes, both
sample sizes.** Measured, not inferred — the probe asserts this on every
character. Structurally impossible per the code (both `match::nearest`'s
sort and `pipeline::nn_candidates`'s sort put the argmax at index 0), and
the assertion confirms it holds in practice.

**b3 (post-decode rewrite): impossible by construction** — no such stage
exists anywhere in `ocrcer-core` after `decode_word` returns. (Measured by
source inspection, not by the probe: `ocrcer-core` has no code path between
Viterbi and the returned string.)

### b2 dominant term (only path for Fate B — confirmed by elimination above)

| dominant term | mode 0 (matcher), n=8579 | mode 1 (net), n=782 |
|---|---|---|
| confusion | 6510 (75.9%) | 351 (44.9%) |
| bigram | 1187 (13.8%) | 118 (15.1%) |
| case | 571 (6.7%) | 142 (18.2%) |
| match | 303 (3.5%) | 171 (21.9%) |
| lex | 8 (0.1%) | 0 |

Net's decoder overrides skew far more toward `match`/`case` dominating and
far less toward `confusion` dominating, relative to matcher — consistent
with the gap-magnitude finding below (a term needs a much bigger raw
advantage to overturn net's typical margin, so when it does win, it's
usually a `case`/`match` clash rather than the shallow `confusion` nudges
that flip matcher decisions constantly).

### Mean top1↔top2 match-term gap (the mechanistic finding)

`w_match * (cands[1].distance - cands[0].distance)`, averaged over all
characters with ≥2 candidates:

| | 20-page sample | 160-page sample |
|---|---|---|
| mode 0 (matcher) | 1.8559 | 1.8985 |
| mode 1 (net, √2) | 11.0982 | 10.8795 |

**Net's typical top1/top2 margin is ~5.7–6x larger than matcher's, at both
sample sizes** — not a fluke. `decode.w_match=1.0` is authored as "the unit
the other three terms are expressed in," and `char_bonus` / `char_bonus_slanted`
/ `case_shape_penalty` (all measured specifically from matcher distances,
per `model/params.tsv`) were calibrated against that unit. Net's margin is
routinely 6x too large for `confusion`/`bigram`/`case`/`lex` (whose
authored magnitudes assume matcher-scale swings) to have a realistic chance
of overturning it — this is exactly why net's Fate B rate is ~11x lower
than matcher's (0.48% vs 5.31% of aligned characters) and why the
`confusion`-dominant share collapses from 75.9% to 44.9%.

### Fate C cross-mode check ("did mode 0 choose the ground-truth cut there")

| Fate-C words (this mode) | other mode aligned instead | rate |
|---|---|---|
| mode 0 (matcher), n=5509 | 260 | 4.7% |
| mode 1 (net), n=5336 | 87 | 1.6% |

The large majority of Fate-C mismatches are **not** "one mode found the
correct cut and the other missed it" — in 95.3% (matcher) / 98.4% (net) of
cases, *neither* mode's decoded word aligns to truth at that position, most
likely genuine segmentation ambiguity (hyphenation, digit-group punctuation,
merged/split tokens) shared by both pipelines rather than a per-mode
decoding difference. Net recovering the correct cut where matcher didn't is
rarer (1.6%) than the reverse (4.7%) — a mild point in matcher's favour on
segmentation specifically, though Fate C's overall rate is close between
modes (15.9% vs 16.5%, above) so this is a second-order effect, not the
main story.

## Named-pair breakdown by fate

None of `2→8, 0→3, 4→0, 8→6, C→S, M→C, T→t` appear anywhere in
`model/confusions.tsv` (76 rows, read in full). The authored pairs are a
different, non-overlapping set (1/l, 1/I, l/I, 1/|, l/|, 0/O, O/o, 5/S, 8/B,
2/Z, 6/G, 9/g, 7/T, g/q, bracket/brace/quote variants, Ø/⌀, x/×, dash
variants). **There is no existing correction rule for any of the seven
named pairs, in either mode** — so nearly all of their occurrences are
Fate A (the classifier's own uncorrected argmax passes straight through),
confirmed below.

| pair | mode 0 A / B / C | mode 1 A / B / C |
|---|---|---|
| 0→3 | 20 / 0 / 58 | 37 / 2 / 45 |
| 2→8 | 13 / 0 / 20 | 33 / 1 / 22 |
| 4→0 | 11 / 6 / 26 | 15 / 1 / 92 |
| 8→6 | 8 / 0 / 18 | 19 / 1 / 14 |
| C→S | 5 / 0 / 21 | 20 / 13 / 27 |
| M→C | 1 / 0 / 5 | 14 / 0 / 3 |
| T→t | 5 / 0 / 0 | 17 / 1 / 2 |

Net produces every one of these seven misreads *more often in absolute
count* than matcher (each is the model's own top-1 error, not a decoder
artefact) — consistent with the generalisation finding (`ARCHITECTURE.md`
§11, chunk 15) that net's superior unseen-crop top-1 doesn't translate
end-to-end. The one exception worth flagging: **C→S under mode 1 has 13 of
60 occurrences at Fate B** (decoder-introduced, not the net's own top
choice) — the only named pair with a non-trivial decoder contribution, and
it happens under `case`/`confusion` pressure since C/S is a case-adjacent
shape pair even though it is not an authored confusion row. `4→0` is
matcher's single named pair with meaningful Fate B (6 of 43) — likely the
`digit_neighbour` confusion context nudging a lone `4` toward `0` in a
digit run.

## Plumbing checks (task's explicit list)

All measured or inferred by direct source/data reading, not assumption;
labelled individually.

- **Class index mapping** (inferred, safe): net's `log_probs` index space
  matches `Model.classes` by trainer convention (`junk_index = n_classes`,
  `tools/nn/train.py`), enforced *indirectly* at build time via
  `charset_sha256` agreement (`ocrcer-build/src/nn.rs::validate`). **No
  direct runtime assertion of `junk_index == classes.len()` exists in
  `ocrcer-core`** (`ocrw.rs` has zero occurrences of `junk_index`) — a soft
  defense-in-depth gap, not an active bug under the current build pipeline.
- **Junk index exclusion** (measured, correct): `pipeline::nn_candidates`
  filters `i != junk_index` before building any candidate — junk never
  enters the candidate list.
- **Candidate sort order** (measured, consistent): both `match::nearest`
  and `pipeline::nn_candidates` sort with the identical tie-break (lower
  class index wins ties among equal scores).
- **Distance sign/units** (measured, consistent direction, inconsistent
  magnitude): both scorers use smaller-distance-is-better; net's
  `distance = scale * -ln(p)` and matcher's weighted-L2 share sign and are
  nominally the same unit by construction of `w_match`/`nn.scale`, but their
  *typical gap magnitude* differs ~6x (above) — this is the calibration
  gap, not a sign or unit-direction bug.
- **Confusion/case rules vs. distance assumptions** (measured, no direct
  coupling): `decode/confusion.rs`'s `Confusions::adjust` reads only
  class/context bits and authored log2 adjustments — it never reads a raw
  distance value. The *indirect* dependency is that `char_bonus`,
  `char_bonus_slanted`, and `case_shape_penalty` were measured specifically
  against matcher-scale match-term swings (per their `model/params.tsv`
  provenance rows), so their fixed magnitude is calibrated for one scorer's
  gap distribution and not the other's.

## What this is, and is not

**No plain code bug was found in mode-1 plumbing.** Sort order, sign,
junk exclusion, and the b1/b3 impossibility proofs are all confirmed
correct by direct inspection and by the probe's own zero-violation count.

**The actual finding is a calibration/design-compatibility gap**: `nn.scale=√2`
was chosen by a valid, pre-registered CER-minimising grid search
(`2026-09-26_c15_measure.md` Step 1) that optimised only the scale factor's
effect on end-to-end CER, and never checked whether the resulting top1/top2
gap distribution stayed compatible with the fixed `w_match`/`confusion`/
`bigram`/`case`/`lex` weights — even though `nn.scale`'s own description in
`model/params.tsv` promises exactly that compatibility ("so decode::viterbi's
scoring formula stays scorer-agnostic"). The practical consequence: net's
much-higher raw top-1 accuracy on unseen crops (99.27% vs matcher's 93.16%,
per `2026-09-26_c15_generalisation.md`) survives into the decoder almost
unchanged (Fate A 83.6%, Fate B only 0.48%) because the decoder's
correction terms can almost never outweigh net's typical margin — but this
means net's *own* systematic errors (the seven named pairs above, all more
frequent under net) also survive uncorrected, at a higher absolute rate
than matcher's did, because none of them are covered by an authored
confusion row and the ones that would be case/digit-context adjustments are
too small relative to net's gap to fire.

This is described, not fixed, per the task's instruction — a fix (e.g.
re-deriving `char_bonus`/`case_shape_penalty`/confusion magnitudes to be
scorer-relative, or re-fitting `nn.scale` against gap-compatibility rather
than CER alone, or authoring confusion rows for the seven pairs) is a
separate §11 entry for `ocrcer-architect` to decide, not this diagnostic.

## Gate assessment: NOT CLEARLY MET
# Inserted spaces fell substantially (727 -> 503) but are nowhere near the
# cut-off level of 20 -- the fix recovers roughly a third of the spurious
# insertions the un-pooled per-fragment rule was making, not the great
# majority the gate implicitly expects.
#
# Deleted spaces moved the WRONG way: 377 -> 498, further from the cut-off
# arm's 721 but away from the pre-fix 377 this gate asked to hold near, not
# toward it. Word recall fell 2.8 points as a direct consequence -- pooling
# is now causing some fragments to under-split real word spaces that the
# un-pooled (single-fragment) rule used to catch correctly.
#
# Net effect on the metric that matters most (word F1) is a wash: 65.388% ->
# 65.234%, essentially flat, with CER very slightly improved (12.600% ->
# 12.306%) and WER improved by 2.5 points. The fix is a real, substantial
# reduction in the specific defect it targeted (spurious intra-word splits),
# but it introduces a smaller, opposite defect (some real inter-word spaces
# now pooled into the intra-word class) that the gate as stated does not
# consider acceptable.
#
# Likely mechanism (not verified further -- implementation is exactly as
# specified in ARCHITECTURE.md section 11 and CLAUDE.md forbids inventing
# scope beyond the spec): an invoice band frequently contains many narrow,
# mostly-numeric column fragments alongside one or two fragments with real
# running text. Pooling all of a band's gaps as x-height multiples means the
# numerous tight intra-column gaps from the narrow fragments can outweigh the
# few real word-space gaps from the text-bearing fragment(s) in the same
# pool, pulling the shared valley threshold up past some real spaces. This is
# the opposite failure mode from the one the fix targets, on the same
# mechanism (one shared threshold applied to structurally dissimilar
# fragments), and is a genuine finding for ocrcer-architect to adjudicate --
# not a bug in this implementation of the specified algorithm.
#

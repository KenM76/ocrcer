# Chunk 15 diagnosis: train/serve skew and mis-segment confidence

Architect-assigned diagnosis, **no parameter, weight, or default change**.
Follows `docs/measurements/2026-09-26_c15_measure.md`'s "Chunk 15 step 2
fails" result (`match.classifier=1` loses end to end by +1.09 pp CER /
+2.24 pp line-matched CER against 160 unseen finfilings-train pages, despite
winning on isolated train crops, 95.75% vs 91.99%) and `ARCHITECTURE.md` §11's
three candidate causes. This measures candidate (1), train/serve skew, then
does the cheap check on candidate (2) the same entry asks for once (1) is
disposed of.

Scope discipline observed throughout: no read of `finfilings`,
`finfilings-val`, `pages-cov`, any fixture, or `bench/ident`.
`finfilings-train-unseen` (320 pages, distinct from the scoring-only
`finfilings` set) was read for the hypothesis-2 check only, and only its
aggregate edge-kind/confidence counts are reported below — no page text.

## Verdict on hypothesis (1): real, but rare, and not shown to move accuracy

**Measured: two independent train/serve skew sources exist in code, both
confined to one function.** **Measured: on a 124-row sample of on-path real
training crops, the resulting numeric divergence is nonzero on 3 rows
(2.4%) and does not change the net's top-1 prediction on any of them** (see
§3). Given that, hypothesis (1) is not shown to be the dominant driver of
the end-to-end loss, though the sample is small enough that this is an
**inferred** conclusion, not a proof of absence — see the caveat in §3.4.
Rule 4 ("every pipeline stage is written exactly once") is nonetheless
violated by the code finding in §2, independent of its measured impact, and
should be fixed on its own terms.

## 1. Where inputs are built for a lattice candidate

**Runtime** (`crates/ocrcer-core/src/pipeline.rs`, `read_word`, and
`crates/ocrcer-core/src/layout/segment.rs`):

```
segment::crop(lat, labels, page_width, e)        // pipeline.rs:~388
  -> Glyph { ink, width, height, x, y, .. }        // segment.rs:461-493
Glyph::input(&line)                                // segment.rs:161-172
  -> GlyphInput { ink, width, height,
                  baseline_dy: line.baseline_dy(self.y),   // lines.rs:~495
                  x_height: line.x_height }
feature::extract_with_grid(&input)                 // pipeline.rs:~392
model.standardise(&raw)                             // pipeline.rs:~393, ocrw.rs
net.forward(&grid, &normalised)                     // pipeline.rs:~395
```

`segment::crop` (segment.rs:461-493) fills `ink` from the mask **only where
the pixel's connected-component label is in the edge's own allowed-label
set** (`edge_labels(lat, e.from, e.to)`); any foreground pixel inside the
same bounding box belonging to a different component is zeroed. `baseline_dy`
comes from `TextLine::baseline_dy` (lines.rs:495-497), `self.baseline - top`,
on the **internal, unrounded `f32` deskewed-space baseline**.

**Trainer** (`crates/ocrcer-bench/src/bin/nn15_dump.rs`, the (b) real-crop
positive-example path, function `dump_real_and_nonpath`, approx. lines
1150-1200):

```rust
let mut ink = vec![0u8; (rw * rh) as usize];
for yy in 0..rh {
    for xx in 0..rw {
        let src = ((ry + yy) * mw + (rx + xx)) as usize;
        ink[(yy * rw + xx) as usize] = mask[src];   // flat rectangular copy
    }
}
let baseline_dy = (deskewed_baseline - f64::from(ry)) as f32;
let input = GlyphInput { ink: &ink, width: rw, height: rh, baseline_dy, x_height: dline.x_height };
```

where `deskewed_baseline = f64::from(dline.baseline) - f64::from(dline.rect.x) * slope`
attempts to invert `pipeline.rs`'s `unshear`, starting from the **public,
already-`.round()`ed, already-unsheared** `Line.baseline` the engine
returned (`pipeline.rs`, `unshear(line.baseline.round().max(0.0) as u32, ...)`,
~line 361), not the internal float `TextLine.baseline` the runtime itself
reads.

**Finding, code-level (measured, by inspection):**

1. **Ink construction skew.** The dump's real-positive path copies every
   foreground pixel in the rectangular bounding box, unfiltered by
   component label. The runtime's `segment::crop` filters to the edge's own
   labels only. Any crop whose bounding box overlaps another component's
   ink (touching or kerned characters -- an already-documented risk,
   `ARCHITECTURE.md`'s 2026-09-23 "t/h overlap" entry) is trained on a
   different `G` than production ever serves. This reaches every grid-derived
   dimension of `X` (0..103, plus ink fraction at 104).
2. **Baseline reconstruction skew.** The dump inverts a rounded, clamped,
   already-unsheared public value instead of reading the unrounded internal
   one it does not have in scope at that call site. This reaches only the
   two baseline-relative geometry dims, `X[105]` (height above baseline) and
   `X[106]` (depth below baseline).
3. **Both are confined to the (b) real-positive path.** The same file's
   (c)(ii) real-negative path and (c)(i) render-junk path both correctly call
   `g.input(&tl)` / `g.input(tl)` -- the shared `Glyph::input` construction --
   so this is a **rule-4 violation isolated to exactly the rows that teach
   the network what each character class looks like**, not a pattern
   throughout the file.
4. **Normalisation is not duplicated.** `Model::standardise` is called
   exactly once in each of the three relevant call sites (`match.rs::nearest`,
   `pipeline.rs::read_word`, `nn15_dump.rs`'s dump), and `Nn::forward` does
   not re-normalise its `features` argument. Ruled out as a skew source.

## 2. Probe: `crates/ocrcer-bench/src/bin/skew_probe.rs`

New binary (bench-only, not core; auto-discovered, no `Cargo.toml` entry
needed, same as `nn15_dump.rs`). For each of the 107 stems in
`bench/splits/nn15_page_split.tsv` (the trainer's own definition of
"training set page"), it:

1. Re-decodes the page with `Engine::recognize_lines` and separately
   rebuilds the identical mask / deskew / labels / bands / lines / word
   spans `nn15_dump.rs` builds (same public calls, same order:
   `binarize::binarize_with` -> `deskew::estimate_with`/`correct_with` ->
   `binarize::binarize_with` -> `underline::strip_underlines` or
   `components::label`+`components` -> `lines::group_with_bands` ->
   `words::split_band_with`).
2. For a capped, evenly-spaced sample of the stem's rows recorded in
   `nn15b/real_{train,val}_meta.tsv`, locates the corresponding decoded
   `Line`/`Word`/`CharBox`, checks the recorded codepoint still matches,
   finds the rebuilt word span whose x-range overlaps the decoded word most,
   builds that span's lattice (`segment::build_with`), and finds the lattice
   edge whose cropped box (`segment::crop`) exactly matches the decoded
   `CharBox.rect` -- i.e. the actual runtime candidate for that exact
   character.
3. Computes that edge's true `G`/`X` via `Glyph::input`, `extract_with_grid`,
   `model.standardise`, and diffs it against the bytes `nn15_dump.rs` wrote
   to `nn15b/real_{train,val}_{G,X,y}.{f32,u16}` at that row's offset (read
   directly, not re-derived).
4. Runs the loaded `Nn` forward on both the dump-fed and the runtime-fed
   inputs and compares top-1 (junk class excluded, ties broken low-index,
   mirroring `pipeline.rs::nn_candidates`) against the recorded label.

Model used: `model/out/ocrcer.ocrw`, built fresh in this session with
`--nn D:/Dev/ExcludedPrivate/ocrcer/nn15b/weights/cpu_det_run1`. **Verified
config-consistent with the nn15b dump** (measured): a control build of the
same source tables without `--nn` produced `build_id d2997ef3`, an exact
match to `nn15b/model_meta.json`'s recorded `build_id` -- so no table/param
drift confounds this comparison; the `--nn` build's own different id
(`05deaa58`) is expected, since `build_id` is a CRC32 over the whole `meta`
blob and the `nn` table is spliced in before hashing
(`ocrcer-build/src/emit.rs`).

### 3.1 Skew is real but rare, in this sample

Of 208 sampled rows, 124 (59.6%) reached a matched runtime candidate; the
rest were lost to probe-methodology friction, not skew (§3.3). Of those 124
matched rows, exactly **3 (2.4%)** show any numeric difference at all
between the dump-fed and runtime-fed `G`/`X` (`delta_G_nonzero_rows`,
`delta_X_other_dims_nonzero_rows`: 3 of 124). When it occurs the divergence
is large in absolute terms -- `delta_G_max = 1.0` (a full ink/no-ink flip at
at least one grid cell) and `delta_X_max = 2.81` standardised units -- fully
consistent with the ink-filtering mechanism in §1 (an overlapping neighbour
component's ink entering the dump's flat rectangular copy but not the
runtime's label-filtered crop). This is the same class of event
`nn15_dump.rs`'s own (c)(ii) path already tracks and counts nonzero
(`junk_nonpath_lattice_rebuild_mismatches: 4552` in `nn15b/summary.json`,
albeit for a different population of rows) -- a rare-but-real occurrence
rate is the documented pattern in this codebase, not a surprise.

### 3.2 The baseline-reconstruction skew source did not fire at all here

`delta_X_baseline_dims_nonzero_rows: 0` across all 124 matched rows: the two
baseline-relative geometry dims (105, 106) were **bit-for-bit identical**
between dump and runtime on every sampled row. **Inferred**: this is
consistent with the sampled finfilings-train pages having near-zero
estimated deskew slope (`unshear` is an exact identity when `slope == 0.0`,
`pipeline.rs`'s `unshear`), which would make the dump's flawed inversion of
`unshear` lossless by construction on these pages regardless of the
rounding step. This measurement does not establish that the baseline skew
source is inert on any page with non-trivial measured skew -- it was not
exercised in this sample -- only that it did not fire here. The ink-filtering
source (§3.1) is the one shown to be non-hypothetical.

### 3.3 Where the other 84 sampled rows went, and why that is not itself skew evidence

- `codepoint_mismatch: 35` (16.8% of sampled) -- the re-decode's character at
  the recorded `(line_idx, word_idx, char_idx)` is a different codepoint than
  `nn15b` recorded there. **Measured** as a mismatch; **inferred** cause is
  index fragility (line/word/char list order depending on any segmentation
  change between when `nn15b` was dumped and this session's rebuild), not
  itself the train/serve skew this diagnosis targets -- it is a separate
  finding, noted here for honesty rather than folded into the skew numbers.
- `no_word_span: 47` (22.6%) -- the probe's own geometric re-match (locate a
  `TextLine` by y-midpoint, then the word span with greatest x-overlap)
  failed to find a candidate. **Inferred** to be probe methodology loss
  (the same reconstruction-matching friction `nn15_dump.rs` itself reports
  a nonzero rate for), not a runtime-vs-trainer skew signal.
- `no_edge_match: 0` -- whenever a word span was found, the exact-box lattice
  edge was always found too. No sign of a segmentation-level skew source
  distinct from the two identified in §1.

### 3.4 Net accuracy: identical on dump-fed vs runtime-fed inputs, on this sample

`accuracy_dump_fed = accuracy_runtime_fed = 0.9677` (120/124 correct, exact
match to four decimal places) on the 124 matched rows, including the 3 rows
with nonzero `ΔG`/`ΔX`. **Measured**: the net's prediction did not flip on
any of the 3 divergent rows in this sample. **Inferred, with an explicit
caveat**: n=3 divergent rows is too small to rule out that skew ever flips a
prediction elsewhere in the ~33,000-row training set; it only shows that,
where sampled, the skew found was not large enough relative to this
particular net's decision boundary to change the top-1 answer. Combined with
§3.1's rarity, hypothesis (1) is not shown to be the dominant driver of the
measured +1.09/+2.24 pp end-to-end loss.

## 4. Cheap check on hypothesis (2): mis-segment share of winning candidates

New binary, `crates/ocrcer-bench/src/bin/segkind_probe.rs`. For each page in
a sample of 30 pages from `finfilings-train-unseen` (distinct from every
forbidden set), it decodes once under `match.classifier=0` and once under
`match.classifier=1` (an explicit `--set`-style override via
`ocrcer_bench::knobs::set`, same mechanism `ocr.rs` uses -- the shipped
model's own authored default stays 0, per the prior chunk-15 entry), rebuilds
each decoded word's lattice the same way as `skew_probe.rs`, and for every
decoded character finds the lattice edge whose cropped box matches, reading
off its `EdgeKind` (`Single`/`Merge`/`Split`) and the engine's own reported
`CharBox.confidence`. Self-referential against the decoder's own bookkeeping,
not against ground truth -- no alignment logic, no page text read.

```
{
  "arm": "classifier=0 (matcher)",
  "total_chars": 33809, "no_edge_match": 3750,
  "merge_or_split": 1988, "merge_or_split_frac": 0.0588,
  "high_conf": 17860, "high_conf_merge_or_split": 1011,
  "high_conf_merge_or_split_frac_of_high_conf": 0.0566,
  "mean_conf_single": 0.7335, "mean_conf_merge_or_split": 0.6810
}
{
  "arm": "classifier=1 (net)",
  "total_chars": 33966, "no_edge_match": 3796,
  "merge_or_split": 2197, "merge_or_split_frac": 0.0647,
  "high_conf": 33724, "high_conf_merge_or_split": 2172,
  "high_conf_merge_or_split_frac_of_high_conf": 0.0644,
  "mean_conf_single": 0.9831, "mean_conf_merge_or_split": 0.9796
}
```

**Measured:**

- The **share of winning candidates that are mis-segments** is close
  between arms: 5.88% (matcher) vs 6.47% (net), +0.59 pp. Not, by itself, a
  large enough gap to explain the measured end-to-end loss.
- The **matcher's confidence measurably distinguishes segmentation
  quality**: mean confidence 0.7335 on clean single-atom edges vs 0.6810 on
  merge/split edges (a 0.052 gap), and only 52.8% of all characters clear
  the 0.8 "high confidence" bar.
- The **net's confidence does not**: mean confidence 0.9831 on single-atom
  edges vs 0.9796 on merge/split edges (a 0.0035 gap, roughly 15x smaller),
  and **99.3% of all characters** (33,724 / 33,966) clear the same 0.8 bar
  -- i.e. under `classifier=1`, "high confidence" is close to universal and
  carries little information about whether the winning edge was a clean
  single-glyph crop or a merge/split.

**Inferred**: this is consistent with the new, matcher-silent confusions
reported in `2026-09-26_c15_measure.md` (`2->8`, `0->3`, `C->S`, `M->C`,
etc.) being delivered at high stated confidence under `classifier=1` --
the net does not appear to hedge on the same cases the matcher's margin
already flags as less certain, which would make its wrong answers land with
a *more* trustworthy-looking score than the matcher ever gives its own wrong
answers on the same kind of input. This is a plausible contributor to the
end-to-end loss distinct from segmentation share itself, and from train/serve
skew -- but it is a correlational read of an aggregate statistic, not a
per-error causal trace, and is offered as a lead for whoever picks up
candidate (3) (decoder terms tuned to prototype distances) or a recalibration
of the net's confidence curve, not as a finding to act on unilaterally here.

## 6. What this does and does not settle

**Settled (measured):** two independent train/serve skew sources exist in
`nn15_dump.rs`'s real-positive dump path (§1, §2) and are a rule-4 violation
regardless of impact; one of them (ink-filtering) is shown to fire on a
measurable but small fraction of real training rows (§3.1); on the sampled
rows where it fires, it did not change the net's top-1 answer (§3.4); the
net's winning-candidate mis-segment share is close to the matcher's, but its
confidence signal is far less selective for segmentation quality than the
matcher's is (§4).

**Not settled:** whether hypothesis (1) contributes anything to the
end-to-end loss on the full unseen-page evaluation (this diagnosis sampled
124 matched training-page rows, not the 160 unseen pages the loss was
measured on, per the constraint against re-running that scoring set);
whether candidate (3) (decoder terms tuned to prototype distances) is a
larger contributor than either (1) or (2); and whether recalibrating the
net's confidence curve alone would close any of the measured gap. All three
remain open for the architect to route to a next chunk.

## 7. Rule-4 fix, verified (2026-09-26, branch `c15-dumpfix`)

Per decision 1 above. `nn15_dump.rs`'s (b) real-positive path no longer
builds `ink` as a flat rectangular copy of the recomputed mask, and no
longer rebuilds `baseline_dy` by inverting `pipeline.rs`'s rounded, public
`Line.baseline`. It now defers each on-path character's dump until its
word's lattice is built and verified (the same exact-box check (c)(ii)
already used for its negatives), then reads `G`/`X` through
`segment::crop`'s label-filtered ink and `Glyph::input`'s unrounded
`TextLine::baseline_dy` -- the identical construction `pipeline.rs::read_word`
and (c)(ii) use. A would-be positive whose word never reaches a verified
lattice edge is no longer synthesised another way; it is dropped and counted
in a new `chars_lattice_mismatch` field in `summary.json`, rather than
silently reappearing with skewed `G`/`X`. No core crate changed; `segment::crop`
and `Glyph::input` were already `pub`, so no new accessor was needed. The
shipped test weights (`training_manifest_id`, `nn15b/*`) are untouched -- no
re-dump of the committed corpus, no retrain.

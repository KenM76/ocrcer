--- verdict ---

Rule A alone (this toggle) does not clear its own gate on the full
finfilings corpus, despite clearing it decisively on the one page the rule
was derived to fix (filing__r000022: CER -5.15, line-matched CER -3.71,
both better). pages-cov is untouched (bit-identical to control), so the
regression is confined to real scanned filing pages, not synthetic ones.

top confusions on the toggled finfilings run are dominated by plain
single-character deletions across nearly every common letter --
"e"->"" 1614, "i"->"" 1239, "t"->"" 1209, "r"->"" 1163, "o"->"" 1053,
"n"->"" 930, "a"->"" 854, "s"->"" 708, "f"->"" 587, plus " "->"" 1635 and
"\n"->"" 729 -- a much broader and flatter deletion profile than either the
control finfilings run or the toggled filing__r000022 run individually
show. This pattern (wide, uniform character loss across many distinct
pages, not concentrated on dense-table pages) is consistent with the strip
firing on real prose/signature content elsewhere in the 60-page corpus --
long words, letter-sequences whose 8-connected components merge into a
single wide blob at 0px/em scan resolution, or genuine underlines/rules
whose removal also removed adjoining glyph ink at the L-long boundary the
run-erase touches -- and stripping real ink along with it, not just the
table rule the single audited page has. The per-page worst-page lists
shifted too: several pages not near the top of the control's worst list
(filing__r000033 at 68.02%, filing__r000044 at 64.61%, filing__r000055 at
55.19%, filing__r000583 at 53.76%) are now the four worst pages in the
corpus, well above filing__r000022 itself (34.99%) -- the toggle is hurting
different pages far more than it helps the one it was built for.

This is the escalation-worthy finding: the rule as implemented (component
width >= L, full-length horizontal run erase along that component's own
label) is not safe to ship at lines.underline_strip=1 by default. Left at
its current default (0, guess) per instructions; not flipped. The
architect should look at reading 4's worst-page list and top-confusions
table before deciding whether the fix is a tighter run_floor, a
column/row-rule-specific heuristic (e.g. requiring the run to span the
full component width rather than just exceed L, or requiring near-constant
row thickness), or component-height gating in addition to width.

"Underline strip, second rule: straight bands only, keep crossing strokes,
drop strip debris, and keep what was stripped" (ARCHITECTURE.md section 11,
2026-09-23, last entry, items 1-4). Reworks strip_underlines in response to
the finding above: a band must now be >= 2 consecutive rows, each with
exactly one qualifying run whose x0/x1 agree within 2px of the row before
it; within an accepted band, a column is only erased where its own vertical
ink run is no taller than the band's row count + 1 (a crossing stroke keeps
every pixel); a piece produced by re-labelling a component that was
actually stripped is discarded if it is taller than lines.debris_heights x
h; every accepted band is recorded as a RuleSegment (x0, x1, y0, y1) on
strip_underlines's new StripOutput, unconsumed downstream. Item 5
("Direction recorded") is out of scope for this entry.

an_underlined_word_splits_into_letters_with_the_line_gone and

strokes") measures a touching column's own vertical ink run through the
whole band, which may reach above or below it; a letter stroke or a solid
digit block that touches the rule with no vertical gap produces one
continuous run spanning its own height plus the rule's, far taller than
the band's own thickness (2) plus 1, so that column is preserved whole
rather than split at the band boundary -- the identical mechanism, not a
special case, that protects a `)`'s bowl in
a_crossing_stroke_keeps_its_pixels_through_the_band below. Both fixtures'
expectations were corrected to match: each letter/digit keeps its own body
plus the two rule rows fused to the column(s) where it touches (height 10,
not 8); only the rule pixels strictly between glyphs, where no column
touches them, are erased. Confirmed correct by hand-tracing every column
of both fixtures against the implementation before changing the
assertions, not by re-running until green.

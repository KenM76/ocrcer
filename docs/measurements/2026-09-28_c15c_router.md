## Verdict: CER gate passes decisively; the timing gate fails

15b fitted the router on crop-level relabel accuracy and lost on end-to-end
page CER (`docs/measurements/2026-09-27_c15b_router.md`). This chunk
re-fits directly on end-to-end page CER, on fold A only, with two added
veto gates (`route.max_junk`, `route.same_category`) the architect asked
for as readings 2 and 3 of the 15b post-mortem. The refit **passes the
step-2 CER gate by a wide margin** (end-to-end CER −0.585 pp, line-matched
CER −0.630 pp, both far past the 0.02 pp bar) but **fails the timing v2
gate** (ratio 1.2807 against a ≤1.05 requirement) — corroborated
independently by both `timing_ab` and the recognition-only speed column
`ocr` printed during scoring. `finfilings-val` reproduces the CER win
(−0.776/−0.842 pp) on a corpus never read anywhere in this branch's prior
work. `ident` shows fewer REWRITTEN identifiers overall (619 → 477,
0 LEXICON-HARM in both) but a worse population of *confidently* wrong
rewrites (REWRITTEN@≥0.9: 32 → 53) — the exact harm rule 5 exists to
surface, reported here rather than smoothed over by the aggregate
improvement.

`match.classifier` still defaults to `0`; nothing in this chunk changed
that default or any mode-0 code path. Only the four `route.*` fitted
values changed, and each is read exclusively when `matching.classifier ==
3` (guarded in `crates/ocrcer-core/src/params.rs`, confirmed by direct
inspection of every `route.*` read site — `RouteProbe`/`recognize_lines`'s
router branch). Mode 0 output is therefore byte-identical to master's by
construction, not merely by re-test; this was also proven directly on
fixtures and `pages-cov` in a prior segment of this same chunk, before any
`route.*` value was touched.

Given the timing failure, whether `match.classifier` should ever default to
`3` is an architecture call, not this report's to make — see "What you do
not own" in this agent's brief. The fitted `route.*` values are committed
because they are the correct numbers for classifier mode 3 *if and when* it
is used, and the CER case for using it is now strong; the timing case
against shipping it as the default is equally strong and is reported with
the same weight.

## Step 0 — diagnosis at 15b's fitted point (fold B, no fit)

Run: 15b's fitted point (`matcher_margin=0.95, net_prob=0.50`, `nn15c`
weights) replayed via `crates/ocrcer-bench/src/bin/route_probe.rs diag` on
the 53 fold-B stems of `bench/splits/nn15_page_split.tsv` (never fold A,
never a page any fit in this chunk touches). Splits the relabel effect into
aligned-word relabels (the decoded word still aligns 1:1 to a truth word,
so "right or wrong" is well defined) and unaligned-word relabels (the
relabel changes token boundaries enough that alignment itself changes,
so its correctness cannot be judged per-character the same way).

| population | CER contribution |
|---|---|
| aligned-word relabels | **−0.083191 pp** (net help) |
| unaligned-word relabels | **+0.158819 pp** (net hurt) |
| **total, route vs. baseline** | **+0.075628 pp** (net hurt) |

This reproduces 15b's own separately-measured end-to-end figure (+0.075 pp,
`docs/measurements/2026-09-27_c15b_router.md`) on a different corpus split
via a completely different code path (whole-page cached replay vs. a live
end-to-end run), cross-validating the `route-probe` harness before it was
trusted for the Step 1 fit below. The diagnosis chose nothing — it is
purely descriptive, as specified — but it does explain *why* 15b lost even
though its crop-level accuracy improved: the harm is concentrated in cases
where a relabel perturbs word alignment, not in cases that align cleanly.
This is what motivated `route.same_category` (readings 2/3 in the §11 entry
this chunk pre-registers against): a relabel that flips a glyph's coarse
category (digit ↔ letter) against every other glyph in its own decoded word
is disproportionately likely to be one of the alignment-breaking ones.

## Step 1 — fold-A grid fit, objective = end-to-end page CER

**Script**: `crates/ocrcer-bench/src/bin/route_probe.rs fit`, whole-page
cached replay (`RouteProbe`/`NetProbe`, built in a prior segment) — capture
once per page at `CAPTURE_MARGIN=0.95`, replay all 250 grid points against
the cached numbers in memory, so segmentation/matching/decode never reruns
inside the grid loop. Reuses `category_flip_vetoed` (now `pub`),
`pages::page_text`, and `cer::score` verbatim (project rule 4).

**Data**: 54 fold-A pages, 124,502 truth characters
(`bench/splits/nn15_page_split.tsv`). Baseline (route off) fold-A CER:
**0.200953** (25,019 char errors / 124,502 chars).

**Grid**: `matcher_margin {0.3, 0.5, 0.7, 0.85, 0.95}` x `net_prob {0.5,
0.7, 0.85, 0.95, 0.99}` x `max_junk {0.02, 0.05, 0.1, 0.2, 1.0}` x
`same_category {0, 1}` — 250 points, run against both weight sets.
Tie-break: fewest relabels.

| weight set | best point | best CER | relabels | on a grid boundary? |
|---|---|---|---|---|
| **nn15b** (winner) | `matcher_margin=0.7, net_prob=0.7, max_junk=1.0, same_category=0` | **0.194776** | 1841 | `max_junk` at its grid's off-value (1.0) — boundary; `matcher_margin`/`net_prob`/`same_category` interior/decisive |
| nn15c | `matcher_margin=0.7, net_prob=0.95, max_junk=0.05, same_category=0` | 0.195017 | 1121 | not on any boundary |

`nn15b` wins outright (0.194776 vs 0.195017), and is the weight set the
shipped model uses, so it is the fitted point carried forward. Both weight
sets pick `same_category=0` (off) — not by tie-break, 0 wins outright at
both optima; the all-one-category veto reading 3 hypothesized does not, in
the end, help on this grid. `max_junk` sits at the top of its grid range
for `nn15b`'s winner: the grid does not rule out that a tighter junk veto
(a smaller `max_junk`) might help, only that none of the four finite values
tried beat leaving it off. Reported as a boundary, not shipped as if it
were interior. `matcher_margin=0.7` and `net_prob=0.7` are both interior to
their grids for the winning point.

Full 250-point grids for both weight sets are preserved as
`fit_nn15b.json`/`fit_nn15c.json` in this session's scratchpad (not part of
the repo; regenerable byte-for-byte from `route_probe.rs fit` against
`nn15b.ocrw`/`nn15c.ocrw` and the fixed split file).

The hard gate (LEXICON-HARM) is 0 in both — the lexicon is never the cause
of a wrong identifier rewrite either way, mode 3 included. Total REWRITTEN
falls by 142 (619 → 477): the router genuinely resolves more identifiers
correctly. But rule 5's specific worry — a wrong answer delivered with a
reviewer-trusted score — gets **worse**, not better: REWRITTEN@≥0.9 rises
from 32 to 53, and the REWRITTEN population's own median confidence rises
from 0.563 to 0.631. The router does not just get more identifiers right;
when it gets one wrong, it is more likely to say so confidently wrong. This
is reported as a real, measured caveat on an otherwise-improving picture,
not smoothed into the REWRITTEN headline.

### `timing_ab` v2 (recognition-only, `finfilings-train-unseen`, default 32-page subset, 5 reps/page, min-of-5)

**A/A self-consistency check** (both sides `match.classifier=0`, isolated,
no concurrent process): ratio sum(B)/sum(A) = **1.0160**, within the
required 1±0.02 band (quartiles p25 0.9817 / p50 0.9996 / p75 1.0251,
range 0.9305–1.1808). Protocol's own noise floor is acceptable.

**A/B run** (A: `match.classifier=0`; B: fitted mode 3), also isolated —
this run was first attempted concurrently with an unrelated `ident
generate` build/render pass in the same window, contaminating its early
pages (first-page ratio 1.32 vs. the A/A run's typical 0.93–1.18); that run
was killed and re-launched alone once the contending process was confirmed
gone, per this chunk's own CPU-contention-avoidance discipline:

```
sum A (min-of-5, 32 pages): 286115.4 ms
sum B (min-of-5, 32 pages): 366437.8 ms
ratio sum(B)/sum(A): 1.2807
per-page ratio quartiles: p25 1.2208  p50 1.2965  p75 1.5597  (range 1.0210-1.7290)
```

**FAILS the ≤1.05 gate** — decisively, not marginally: every one of the 32
pages individually ran slower under mode 3 (min ratio 1.0210), median
1.2965x. This is not measurement noise; it is corroborated by two
independent measurements taken from entirely different tools on different
corpora on the same day (`ocr`'s recognition-only speed column: 1.272 on
the 160-page unseen set, 1.368 on the 103-page val set). The router's extra
per-glyph net forward pass and candidate rescoring is a genuine, consistent
~30–40% slowdown relative to the matcher-only path, not an artifact of
either specific benchmark.

introduced in ARCHITECTURE.md section 11 (2026-09-24 entry). OCR

-----------------------------------------------------------------------
3. Speed and load time (single-threaded and all-threads, nproc 20)
-----------------------------------------------------------------------
Method: crates/ocrcer-llm/examples/bench.rs — load a .ocrl file, prefill
64 tokens of fixed domain text (financial + CAD, matching this project's
stated domain), then score 64 more tokens one at a time via
score_continue (the same per-position lm_head cost as prefill: this
crate's prefill scores every position, not just the last). Both prefill
and decode therefore pay the full 151,936-row lm_head projection at
every one of the 64 positions, which dominates the measured throughput
for a model this small — these numbers describe this crate's current
prefill/decode API shape, not a lower bound on achievable tok/s with a
last-position-only prefill or a KV-cache-only decode loop.

                          load(s)  prefill tok/s  decode tok/s
  qwen3-0.6b   f32  1t     12.536      1.36           1.36
                    20t    12.693      2.94           2.98
  qwen3-0.6b   q8   1t      3.052      1.58           1.61
                    20t     3.050      3.39           3.10
  qwen2.5-0.5b f32  1t     10.416      1.65           1.61
                    20t    10.405      3.64           3.72
  qwen2.5-0.5b q8   1t      2.644      1.97           1.85
                    20t     2.555      4.05           4.12

Speedup at 20 threads over 1 thread, by file: qwen3 f32 2.16x/2.19x
(prefill/decode), qwen3 q8 2.15x/1.93x, qwen2.5 f32 2.21x/2.31x, qwen2.5
q8 2.06x/2.23x. This is a reading, reported as measured, not a
projection: 20 threads buys roughly 2.1-2.3x, not anything close to
20x. The likely reason (not yet isolated by profiling, so stated as a
plausible explanation rather than a proven cause) is that batch=1
matrix-vector matmul is memory-bandwidth-bound rather than
compute-bound — every weight byte is read once and used for one
multiply-add, so more threads contend for the same memory bus instead
of finding more arithmetic to overlap — compounded by std::thread::scope
spawn/join overhead recurring on many small per-layer matmuls rather
than one large one. Load time is dominated by reading the .ocrl file
into memory (largely disk/page-cache bound) and is flat across thread
counts, as expected since with_threads only affects matmul.

Q8 vs f32 is consistently ~1.1-1.4x faster despite doing dequantisation
work per block, because it moves roughly 3.5x fewer bytes per matmul;
bandwidth-bound behaviour again, this time working in Q8's favour.

# L1 (isolated marks): fix, measurement, gates

Branch `L1-marks`. Implements `ARCHITECTURE.md` §11's L1 fix as pre-registered
in `docs/measurements/2026-09-26_c15_tableseg.md`: a component (or small
cluster) too small to be a line on its own is attached to the line it
overlaps vertically, or failing that the nearest line, instead of founding a
new line. Model build recipe and corpus per
`docs/measurements/2026-09-26_c15_measure.md`.

## Code

`crates/ocrcer-core/src/layout/lines.rs`:

- `Params::isolated_mark_height_fraction: f32` (new field, doc comment carries
  the measurement below).
- `Band::overlaps_y` (new helper: true vertical overlap between two bands'
  ink extents).
- `merge_isolated_marks(bands: &mut Vec<Band>, p: &Params)` (new pass): for
  each band whose tallest member's height is at most
  `isolated_mark_height_fraction` of a candidate host's median member height,
  merge into the host it overlaps vertically, or, failing that, the nearest
  host by vertical gap, capped by the existing `Params::mark_reach_fraction`
  (reused rather than adding a second guess about the same question). Runs to
  a fixed point, same termination argument as `fold_marks`.
- Call site in `group_with_bands`, immediately after `fold_marks` and before
  `split_baselines`:
  ```rust
  fold_marks(&mut bands, p);
  merge_isolated_marks(&mut bands, p);
  ```
  Ordering matters: `fold_marks` is x-overlap-gated (right host for an
  `i`-dot over its own stem) and would misfire on a numeric column where
  every row shares the same x-range; `merge_isolated_marks` is vertical-
  overlap-gated instead, which is what separates one table row from another.
  It must run before `split_at_column_gaps`, which cuts a band into per-
  column fragments — post-split, a lone comma-band would already be one
  fragment among many and there would be no "column" left for it to escape.
- Unit test `isolated_thousands_separators_join_their_digit_row`: synthetic
  numeric-table line, hand-built bitmap, three digit rows each carrying a
  separated comma below baseline; asserts each comma's band count collapses
  into its row rather than seeding a line of its own.

`crates/ocrcer-core/src/params.rs` and `model/params.tsv`: added
`lines.isolated_mark_height_fraction` as row 81 (f32, authored, tune=yes),
consistent with the existing `NAMES`/`f32_fields`/`set_f32`/`.lines()`
plumbing. Built model now reports 81 param rows, 12 authored (up from the
pre-fix 80/11).

## Criterion and its value

**`isolated_mark_height_fraction = 0.95`, authored.**

Measurement behind it (recorded in the field's doc comment, reproduced here
per the assignment's "report the measurement"): across all 320
`finfilings-train-unseen` pages, at pre-fix line grouping, the height of
every single-member band that seeded a line of its own was measured as a
fraction of the nearest other band's median member height (by vertical
overlap, else nearest gap) — 7,523 samples. The distribution is cleanly
bimodal: every sample from a genuinely isolated mark (an actual one-line
component — a rule, a stray mark, a page furniture glyph) measured at 1.0 or
above; every sample from what turned out to be a stray thousands-separator
comma or similar sub-row fragment measured at or below 0.9412. Nothing fell
in between. 0.95 sits in that empty gap, with headroom on both sides.

The rule this value gates carries no member-count restriction (same as
`fold_marks`), so a small cluster of marks that joined each other at seeding
but never found a host is merged by the same test as a single isolated one.

## Step 2 — mode 0 with L1 vs mode 0 control

Same 160-page cohort: `finfilings-train-unseen`, stride 2, offset 0
(deterministic alphabetic order), `match.classifier=0`, model built via
`cargo run --release -p ocrcer-build -- write 16,20,24,32,48 21,26,36,56
model/out/ocrcer.ocrw --nn D:/Dev/ExcludedPrivate/ocrcer/nn15b/weights/
cpu_det_run1`. L1 toggled via the existing `ocr --set` override on one build
(`lines.isolated_mark_height_fraction=0.0` disables the merge unconditionally
— the gate `small.max_height() > fraction * median` is then true for every
band, since a band has at least one pixel of height, so no merge ever fires;
confirmed independently by control reproducing `2026-09-26_c15_measure.md`'s
pre-existing classifier=0 baseline numbers exactly).

### Singleton-tiny-band counts

Measured at the `group_with_bands` band-group level (summing member counts
across a band's column-cut fragments, not the final flattened `TextLine`
level — `split_at_column_gaps` runs downstream of `merge_isolated_marks` and
would re-fragment an already-merged band, confounding a diagnostic that
tried to measure this at the flattened level).

| | before (control) | after (L1) | Δ |
|---|---|---|---|
| singleton bands, total | 77 | 68 | −9 |
| singleton bands, "tiny" (ratio ≤ 0.95 to nearest other band) | 52 | 44 | −8 |

A real but partial reduction: not every tiny singleton merges, because
`mark_reach_fraction`'s reach cap (reused rather than duplicated) leaves some
tiny bands with no host within range — the same reach limit that keeps
`fold_marks` from walking a real short line to the tallest band on the page
applies here too, and correctly declines to merge a tiny band that has no
plausible host nearby.

4. **Wall time ≤ +5%** (same 160-page cohort, recognition only):

   ```
   control:  1633.6s for 160 pages, 10210 ms/page
   L1:       1731.4s for 160 pages, 10821 ms/page
   ```

   Δ = **+5.99% wall-clock, +5.98% ms/page.**

   **FAIL.** Exceeds the ≤+5% gate by about 1 percentage point (roughly
   61 ms/page over the 5%-of-10210 budget of ~511 ms/page). Reporting this
   as a fail rather than rounding it into the noise, per CLAUDE.md rule 8
   ("Benchmark losses are reported as prominently as wins. If a gate did not
   pass, the chunk is not done."). `merge_isolated_marks` runs to a fixed
   point with an O(bands²) inner scan per round (same shape as
   `fold_marks`), so its cost scales with band count on pages with more
   candidate singleton bands — plausible cause, not yet isolated or
   profiled; that is a question for whoever picks this back up after
   adjudication, not a self-serve retune of the criterion to dodge the gate.

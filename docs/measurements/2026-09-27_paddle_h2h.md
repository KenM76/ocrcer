# PaddleOCR head-to-head (2026-09-27)

Comparison baseline only. Nothing from PaddleOCR (Apache-2.0,
`PaddlePaddle/PaddleOCR`) enters `ocrcer-core`, any other OCRcer crate, or
the model file. This is measurement, not integration.

**Headline, stated plainly up front because the honesty rules require it,
not buried under the wins: PaddleOCR beats OCRcer on every corpus, every
document category, and every metric measured in this round.** There is no
metric below where OCRcer's own already-published numbers come out ahead.
See "Where each engine wins" for the full, unsoftened statement of that.

### Pipeline configuration

```python
PaddleOCR(
    use_doc_orientation_classify=False,
    use_doc_unwarping=False,
    use_textline_orientation=False,
    enable_mkldnn=False,
)
```

Two deliberate departures from PaddleOCR's own literal defaults, both
disclosed rather than hidden:

- **`use_doc_orientation_classify=False`, `use_doc_unwarping=False`,
  `use_textline_orientation=False`** — an interpretation of the task's
  wording ("the default English/Latin pipeline, text detection plus
  recognition, with no document-structure or VL model") as scoping
  strictly to detection + recognition. Verified this is not a
  face-saving choice: a smoke test with all three enabled on a flat,
  un-rotated, un-warped rendered page made results *worse* (UVDoc
  unwarping truncated "30 days" to "30 da" and shifted a box's left edge)
  and cost ~26% more wall time for a correction these pages never need.
  Decided before any comparative CER number existed for either
  configuration, so it is a scoping call, not a result-driven one.
- **`enable_mkldnn=False`** — a pure compatibility workaround, not an
  accuracy choice. Left at its own default, PaddleOCR 3.7.0 /
  PaddlePaddle 3.4.0 on this machine crashes on the first detection call
  (`NotImplementedError: ConvertPirAttribute2RuntimeAttribute not support
  [pir::ArrayAttribute<pir::DoubleAttribute>]`, an
  oneDNN/PIR-executor incompatibility in `paddlex`'s auto-selected
  `run_mode="mkldnn"`). Disabling oneDNN routes around the crash and
  changes nothing about which model or weights are used, only which
  backend kernel executes them.

### Reading-order reconstruction

PaddleOCR's detector returns one box per text line/region with no
paragraph or reading-order structure. Reconstruction rule (implemented
once, in the driver script, applied uniformly to every page):

1. Compute each box's vertical center.
2. Sort boxes by vertical center, then fold greedily into rows: a box
   joins the running row if its center is within half that row's mean box
   height of the row's running mean center, else it starts a new row.
3. Sort each row's boxes left-to-right by their own left edge (`x0`).
4. Join each row's texts with a single space; join rows with a newline,
   ordered top-to-bottom by row mean center.

Driver script (not part of the crate; PaddleOCR is out-of-process Python,
per `CLAUDE.md` rule 4): scratchpad copy referenced below; not committed to
the repo since it drives a tool this project deliberately does not depend
on.

## 1. Corpora and scoring tool

Same page images OCRcer's own scoring uses, from
`docs/measurements/2026-09-25_score_12b.md`:

- **finfilings** (60 pages, private, real financial-filing content
  extracted from an already-rendered parquet dataset — not a scan, per
  `docs/measurements/2026-09-23_finfilings_audit.md`). Page text stays
  local; nothing from it appears below.
- **pages-cov** (625 pages, synthetic, license-clean, content-neutral to
  quote) — 7 categories x ~90 pages: currency, drawing, invoice, prose,
  statement, technical, twins (currency is 85, not 90).

New tool: `crates/ocrcer-bench/src/bin/paddle_score.rs` (`paddle-score`
binary, registered in `crates/ocrcer-bench/Cargo.toml` behind the existing
`pages` feature). Calls `ocrcer_bench::cer::{score, token_score,
line_matched_score}` and `ocrcer_bench::ident::is_identifier_shaped`
unmodified — the same functions `bin/ocr.rs` and `bin/ident.rs` call, per
`CLAUDE.md` rule 4 (a stage or metric is implemented exactly once). It does
not link `ocrcer_core::pipeline::Engine` or read any `.ocrw` file; Paddle's
reconstructed text is scored as plain files against the corpora's own
truth JSON.

Per-category CER is a **page-mean** (mean of each page's own CER), matching
`2026-09-25_score_12b.md` section 2's own stated method exactly, not a
corpus-total character-weighted figure — the two tables below are directly
comparable, category by category.

Commands:

```
cargo build --release -p ocrcer-bench --bin paddle-score
paddle-score cer bench/pages-cov <paddle-cov-out> --worst 10 --csv <cov.csv>
paddle-score cer <finfilings-pages> <paddle-fin-out> --worst 10 --csv <fin.csv>
paddle-score ident bench/ident <paddle-ident-out> --stride 3 --offset 0
```

PaddleOCR wins all seven categories. `twins` is the worst category for

largest there too (-9.863pp) — the category both engines find hardest is
also where the gap is widest, not narrowest.

`technical` (CAD/engineering symbol content — dimension callouts,
tolerance stacks) is the category closest to `docs/ARCHITECTURE.md` §2's
charset table and this project's stated class-2 target. PaddleOCR still
wins it outright (1.720% vs 5.855%), though its errors there are not
nothing: manual inspection of the worst page
(`lato__regular__technical__14px`, PaddleOCR's single highest-CER page in
this corpus at 11.54%) shows PaddleOCR's failures on this content are
mostly **whitespace collapse** between adjacent short tokens ("AREA 0.42"
-> "AREA0.42", "to +85" -> "to+85") and **symbol substitution** on the
diameter and degree-Celsius glyphs (Ø -> ∅, °C -> ℃), not dropped or
garbled digits. That symbol confusion is exactly the class of error
`docs/ARCHITECTURE.md` §2's charset table and this project's confusion
table exist to catch — it is a live failure mode for PaddleOCR too, just a
much smaller one in aggregate here.

## 5. Identifier preservation

**Not a like-for-like comparison — methodology differs, and the
difference favors the easier bar being reported here for Paddle. Read
the two numbers as pointing in the same direction, not as a strict head
to head.**

- **OCRcer** (`2026-09-25_ident_corpus.md`, fitted, full 1855-page corpus,
  position-aligned per-word harness): 61.509% exact, 18.506%
  dropped/garbled, 19.984% REWRITTEN (a different identifier or a
  dictionary word). LEXICON-HARM (the narrow, gated condition) is 0.
- **PaddleOCR** (this round, 619-page stride-3 subsample of the same
  corpus — a full 1855-page run was not completed this round; see below —
  page-level, order-free check: does the truth token appear anywhere on
  the page as a whitespace-delimited token, regardless of position):
  **96.328% verbatim-preserved** (2046 of 2124 identifier-shaped tokens).

The Paddle figure is measured under a much easier bar (page presence, not
positional agreement) than OCRcer's own aligned harness, so **61.509% and
96.328% are not directly comparable numbers** and neither should be quoted
against the other as if they were. What is comparable, and worth stating:
of the 78 PaddleOCR misses in this subsample, the three inspected by hand
were all single-character confusions on the same identifier, never a
rewrite into a dictionary word:

- `Ø12.5` -> `012.5` (diameter symbol read as digit `0`)
- `M8x1.25` -> `M8×1.25` (ASCII `x` read as the true multiplication sign)
- `PO-88213` -> `P0-88213` (letter `O` read as digit `0`)

This is a spot check of 3 of 78 cases, not an exhaustive audit — it is not
a claim that PaddleOCR never rewrites an identifier into a dictionary
word, only that none of the sampled failures did. On this narrow point
(rule 6's specific concern — never silently rewriting an identifier into
a plausible dictionary word) both engines currently look safe: OCRcer's
own measured LEXICON-HARM is 0, and nothing sampled here from PaddleOCR
did it either.

**Why 619 of 1855 pages, not all of them:** at the per-page rate measured
here (~4s/page once running alone; considerably slower earlier while
sharing a CPU core with the other two corpus runs), the full corpus was a
multi-hour run. A stride-3 subsample (every third page in the corpus's own
sorted order, 619 pages, 2124 identifier-shaped tokens) was run instead to
keep this round bounded. State this plainly rather than silently
completing only part of the corpus: **this identifier result rests on
about a third of the corpus OCRcer's own number was measured against**,
and should be read as a directional check, not a final figure.

## 6. Confidence calibration — not measured this round

PaddleOCR's own API does emit a per-recognition confidence score
(`rec_scores`), unlike `ocrs`, which reports none at all — this is a real
difference between the two comparison baselines and should not be
flattened into "neither reports confidence." The driver script used in
this round did not capture or aggregate that score, so **no reliability
curve or expected-calibration-error number for PaddleOCR exists yet**.
This is a gap in this measurement round, not a claim that the comparison
is impossible — flagging it as a specific, addressable gap for a future
round rather than silently omitting it or conflating it with `ocrs`'s
structural inability to report a score at all.

## 7. Corpus biases — the same three `vs_ocrs.rs` already discloses, and they apply here too

Both corpora are the same ones the `ocrs` comparison uses, so the same
three disclosed biases (`crates/ocrcer-bench/src/bin/vs_ocrs.rs` module
doc) carry over unchanged:

1. **Favours OCRcer.** The corpus is confined to `charset.tsv`, a charset
   chosen to fit OCRcer's own test. PaddleOCR had no such say and is
   still decisively ahead despite it.
2. **Favours OCRcer, and matters most here.** Neither corpus contains
   noise, skew, or scanner blur. finfilings is extracted from an
   already-rendered parquet dataset, not a scan; pages-cov is a synthetic
   render. **This round tests document classes 1 (digital-born print) and,
   loosely, 2 (CAD-style technical/symbol content) — it says nothing
   about classes 3 (clean office scan) or 4 (degraded scan).**
   `docs/FEASIBILITY.md` §5 already projects OCRcer losing to a trained
   CNN specifically on class 4's noise robustness; that projection is
   untested by this round, not contradicted or confirmed by it. What this
   round adds is a harder finding: **OCRcer is currently well behind
   PaddleOCR even on the two classes its own thesis expected it to win.**
3. **Favours neither, damages both equally.** The pages are rasterised
   two-level with no dropout control (9.52% of single-contour glyphs at
   14px/em arrive as 2+ disjoint pieces, per the `vs_ocrs.rs` measurement);
   both engines see the identical page images, so this affects both
   scores, not the comparison between them.

## 8. Where each engine wins — stated once, plainly

**PaddleOCR wins.** Every corpus, every category, every metric measured in
section 3 and section 4 — twelve corpus-level rows and seven per-category
rows, twenty-six numbers total, PaddleOCR ahead on every one, several by
an order of magnitude. Section 5's identifier check does not overturn
this; if anything it shows PaddleOCR preserving identifier-shaped text
about as safely as OCRcer already does, under an easier bar. There is no
row in this report where OCRcer's own already-published number beats
PaddleOCR's measured one.

This is a clean, unhedged result, and it is reported that way rather than
softened. It is scoped: it says nothing about classes 3 or 4, and nothing
about calibration (section 6). Within its scope — digital-born and
CAD-adjacent content, PaddleOCR's default detection+recognition pipeline,
CPU, this corpus — the finding stands as measured.

## 9. What this implies, and for whom

The gap sizes here (roughly 5x to 14x on CER, not single-digit-percent
deltas) are not the shape of a font-coverage gap `ocrcer-glyphs` fixes by
adding faces to the prototype bank, nor a decoder-weight gap
`ocrcer-linguist` fixes by adjusting a bigram or lexicon weight — those
levers move results by fractions of a percentage point per round, per
every prior chunk's own score-once reports (`2026-09-25_score_12b.md`,
`2026-09-27_score_L1W1.md`). A gap this size, on the classes the project's
own thesis expected to win, is a finding about the constructed
prototype-matching approach's ceiling relative to a modern trained CNN
recognizer even outside its weakest domain (noisy scans) — **that is a
question for `ocrcer-architect`, not a lever this report can hand to
`ocrcer-glyphs` or `ocrcer-linguist`,** per this agent's own scope
boundary: a result implying a feature-vector or architectural rethink
is not this agent's decision to make.

The one concretely actionable, lever-sized item this round does surface:
the `technical`-category symbol confusions found on PaddleOCR's own worst
page (Ø/∅, °C/℃, whitespace collapse around short tokens) are exactly the
class of confusion `docs/ARCHITECTURE.md` §2's charset table exists to
name. Worth checking whether OCRcer's own confusion table already covers
these specific pairs (`ocrcer-linguist`'s territory) since they recur in
CAD-adjacent content regardless of which engine reads it.

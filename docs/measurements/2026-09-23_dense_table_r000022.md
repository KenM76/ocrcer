# filing__r000022 traced — underline/text fusion, not table-rule/cell fusion

Date: 2026-09-23. Author: `ocrcer-runtime`. Model: `model/out/ocrcer.ocrw`
(187 classes, 32 faces, 29,675 prototypes, lexicon 2,477 nodes, bigrams 188
rows, confusions 76 — `Observed`, printed by `ocr.exe`'s own model-summary
line). Corpus: `D:/Dev/ExcludedPrivate/ocrcer/pages/finfilings`, single page
`filing__r000022` only, per instructions (no full-corpus runs).

Trigger: `docs/measurements/2026-09-23_finfilings_deletions.md` attributes
9.4% of the six-page worst-CER sample's deletions to this page and flags its
own categorisation as the weakest link in that report — `Inferred` from a
confusion-pattern signature, never verified against the page image. This
report does that verification and tests the specific hypothesis from
`docs/measurements/2026-09-22_research_classical_techniques.md`'s
2026-09-23 addendum ("dense tables: remove ruling pixels"): that a table
rule touching cell text fuses rule and digits into one component, which a
whole-component filter (`lines.furniture_fraction`, `lines.rule_aspect`)
must then either reject outright (digits deleted) or admit whole (rule
pollutes banding and matching).

**Headline: the hypothesis is wrong as literally stated for this page's
data cells — there is no table rule anywhere in the numeric grid — but a
closely related version of the same mechanism is real and well-evidenced
one row category up: the five underlined section-header lines. `Observed`.**

## Method

`--raw` for the aligned REF/GOT strings, `--layout` and `--layout
--no-decode` for per-band diagnostics, `--worst 500` for the complete
per-page confusion table, `--set lines.furniture_fraction=` and `--set
lines.rule_aspect=` at several values (single-page readings only, both
end-to-end and line-matched CER recorded for each). The page's own PGM
(`filing__r000022.pgm`, 1653x2339, matches `truth.json`'s recorded
`width`/`height`) was loaded with `numpy`/`PIL` for pixel inspection —
inspection only, no OCR logic reimplemented. Component connectivity in the
crops below was checked with a hand-rolled 8-connected flood fill in
Python, matching `ocrcer-core`'s `Connectivity::Eight` — again inspection
only, not a substitute implementation feeding any score.

**Caveat on `truth.json`:** this page's truth is `{"lines": [...]}`, a flat
list of 203 strings with no glyph bounding boxes (`glyphs: []`) and
`px_per_em: 0.0` — a linearised transcript (`source.kind:
"parquet-transcript"`), not a positioned one. `--layout`'s printed `want`
field indexes this list by the loop's running fragment count, not by
content or position match, and desyncs permanently the first time a visual
row's fragment count differs from its truth cell count (confirmed: by
`--layout`'s line 24 the `want` field is already several cells behind the
band it's printed beside). `want` is therefore not trustworthy past the
first desync point and is not relied on below for anything but locating
approximate row order; the `decoded` field (looked up from a real
`Engine::recognize_lines` call, keyed by `(x0, x1, y0)`) and the `--raw`
REF/GOT strings are what the claims below are checked against.

## Finding 1 — the numeric grid has no rule pixels; the hypothesis does not apply there

`Observed`: a per-row and per-column dark-pixel-fraction scan of the whole
page (threshold <128, table region `x 230..1600`, `y 100..2200`) finds no
row above 46.6% dark fraction and no column above 11.2% dark fraction
anywhere in the data-cell region. A drawn table rule spanning a column or
row would read near 90-100% in a thin band; nothing on this page does. A
direct crop of the "Merchandise / $ 2,350$ 2,427 -3.3% ..." row (the first
data row under the first underlined header) shows plain proportional text
on a shaded background band, no ruling of any kind. This page's table is
set as plain whitespace-aligned columns (typical SEC-filing text
rendering), not a ruled grid.

`Observed`: the actual mechanism in the data cells is **touching glyphs at
a very small font** (x-height 9.66-10.4px, cap 13-14px throughout this
region — genuinely tiny type), independent of any rule. A tight 8-connected
flood fill of the `"2,350$"` cell (crop `x 700..800, y 490..518`) finds the
trailing `0` and `$` as one component: bbox width 16px vs. the neighbouring
single-digit components' 8-9px, area 101px vs. ~40px for a lone digit — a
visually confirmed `0$` ligature with zero rendered gap between them (the
`$`'s vertical stroke sits against the `0`'s right edge). That merged
component is fed to the matcher as one blob representing two characters;
the observed output for this exact cell is `"255®"` for truth `"2,350$"` —
consistent with `2`→`2` (correct), the low-area comma mark lost, `3`→`5`
(substitution), `5`→`5` (correct), and the merged `0$` blob matching some
single class landing on `®`. This is a touching-character segmentation
problem (survey doc §4, drop-fall's target case), not a furniture/rule-gate
problem: the merged blob's bbox (16x14px) is nowhere near
`furniture_fraction`'s default 20%-of-page threshold (330.6px on this
page's 1653px width) and its aspect ratio (~1.14:1) is nowhere near a
`rule_aspect` gate at any value that wouldn't also reject ordinary letters.
Counting this cell's isolated comma-mark component separately (area 5-6px,
`min_area` is 2, so it is not speckle-dropped) as a likely contributor to
this page's 19 observed `","→""` deletions.

`Inferred`: the same touching-glyph mechanism, not rule/furniture
filtering, accounts for the bulk of this page's digit- and
punctuation-adjacent substitutions and deletions outside the header rows
(e.g. `"."→""` 44, `","→""` 19, digit-to-digit substitutions in the top
confusions). Not individually re-traced cell by cell past the one worked
example above — that would be a corpus-wide or at least page-wide
cell-by-cell pass, out of this report's single-page/no-full-run scope.

## Finding 2 — the five underlined section-header lines really do fuse rule and text, and it is a large share of this page's deletions

`Observed`: this page has five section-header lines set bold and
underlined, each spanning the header's full text width: `"Full Year 2024
over Full Year 2023"`, `"Local Currency Growth"`, `"U.S. Distribution and
Value-Added Services"`, `"International Distribution and Value-Added
Services"`, `"Global Distribution and Value-Added Services"` (confirmed
present, in that visual order, at `y≈339, 386, 478, 690, 895` by direct
pixel-row scan for long contiguous dark runs, then visually confirmed by
cropping each — every one is underlined, and the rule sits close enough
under the baseline to touch descenders and, on several letters, the
baseline serifs themselves).

`Observed`, per-header connected-component measurement (Python flood fill,
8-connected, on a crop bracketing each header + its underline):

| header (truncated) | truth chars | largest component: area / width / height | width vs. `furniture_fraction=0.2` threshold (330.6px) | aspect (long/short) |
|---|---|---|---|---|---|
| Full Year 2024 over... | 34 | 1,655px² / 256px / 15px | under | ~17:1 |
| Local Currency Growth | 21 | 1,493px² / 228px / ~14px | under | ~16:1 |
| U.S. Distribution and... | 42 | 1,974px² / 326px / ~14-17px | under (barely: 326 vs 330.6) | ~20:1 |
| International Distribution and... | 51 | 2,288px² / 394px / ~14px | **over** | ~28:1 |
| Global Distribution and... | 44 | 2,016px² / 339px / ~14px | **over** | ~24:1 |

Every one of the measured components is a single connected blob covering
most of that header's letters, fused together by the underline stroke
running continuously beneath them — a direct, visually confirmed instance
of "rule touches text, rule and glyphs become one component," exactly the
mechanism the hypothesis names, just located at header rows rather than
table-cell digits.

`Observed`: the outcome splits exactly along the addendum's predicted
fork, and both branches actually occur on this one page, because the five
headers' fused-component widths straddle the default `furniture_fraction`
threshold (330.6px) almost exactly:

- **International** (394px) and **Global** (339px) exceed the threshold —
  `is_glyphish`'s `wide` test drops the whole fused blob as furniture.
  Their truth text (51 and 44 chars) is reduced in the actual page output
  to a handful of short fragments from the few letters whose ink did *not*
  connect to the underline (`". . . . ded Semîcee"`, 19 chars, and
  `". . . . ed Semïcee"`, 18 chars) — everything the blob would have
  carried is gone.
- **Local Currency Growth** (228px) and **U.S. Distribution...** (326px)
  fall *under* the threshold — the fused blob is kept as "glyphish" and
  handed to the matcher as one shape. Output: `"≈b"` (2 chars) for 21 true
  characters, and `"l≈d Se™cæ"` (9 chars) for 42 true characters — the
  blob (plus a couple of unfused stragglers) decodes to a small number of
  wrong characters standing in for the whole word run, rather than being
  deleted outright, but the practical effect on the transcript is nearly
  identical: the header's text is gone either way.

Net count, comparing the five headers' combined truth length (192
characters, `Observed` by direct count from `truth.json`) against their
combined surviving output length (~57 characters, `Observed` by direct
count from the `--raw` GOT string) gives **≈135 characters lost from just
these five lines — roughly 37-38% of this page's 357 observed deletions**,
from lines that are only 10.6% of the page's 1,806 characters. `Inferred`
for the precise deletion attribution (the 135-character gap is a length
differential, not a re-run edit-distance alignment restricted to these five
lines specifically), but the concentration is large enough that the
qualitative conclusion — underline/text fusion is a major, specific
contributor, not a minor one — is not sensitive to that imprecision.

## Finding 3 — a whole-component accept/reject gate cannot fix this without new damage, confirmed by counterfactual

Single-page readings only, both metrics `Observed` from `ocr.exe`'s own
output (baseline: end-to-end CER 40.144%, line-matched CER 37.154%):

| setting | end-to-end CER | line-matched CER |
|---|---|---|
| baseline (`furniture_fraction=0.2`, `rule_aspect=0.0` — shipped defaults) | 40.144% | 37.154% |
| `furniture_fraction=0.05` | 40.199% | 35.770% |
| `furniture_fraction=0.12` (catches all 5 header blobs) | 40.089% | 35.991% |
| `furniture_fraction=0.15` | 40.199% | 36.656% |
| `furniture_fraction=0.5` (effectively disabled) | 40.532% | 42.857% |
| `rule_aspect=3.0` (would also catch all 5, on aspect ratio ~16-28:1) | 38.317% | **45.460%** |
| `rule_aspect=8.0` | 38.870% | 42.691% |

Two things worth separating here, both `Observed`:

1. **`furniture_fraction` lowered enough to drop all five header blobs
   outright (0.05-0.15) moves end-to-end CER by less than 0.1pp either
   way, but does improve line-matched CER by 0.5-1.4pp.** Uniformly
   dropping the fused blob (rather than the mixed keep-some/drop-some
   split the default threshold happens to produce) is a small net
   improvement in genuine recognition quality, invisible in the end-to-end
   number because reading-order noise elsewhere dominates that metric.
   Disabling the gate almost entirely (`0.5`) makes both metrics clearly
   worse — letting the fused blob (and whatever else is that wide) survive
   and pollute banding is worse than dropping it.
2. **`rule_aspect` at either tested value improves end-to-end CER
   (-1.8 to -1.3pp) while making line-matched CER markedly *worse*
   (+8.3pp and +5.5pp).** This is the sharpest single result in this
   report: the end-to-end improvement is a reading-order artifact, not a
   recognition improvement — `rule_aspect`'s aspect-ratio test (long/short
   > threshold) at 3.0 or 8.0 also catches ordinary elongated glyphs this
   page uses constantly (hyphens and minus signs prefix nearly every
   negative percentage: `-3.3%`, `-1.2%`, `-0.6%`, ...), and the genuine
   damage from deleting those shows up in the reading-order-independent
   score even as it happens to reshuffle the end-to-end alignment
   favourably. This corroborates
   `2026-09-22_research_classical_techniques.md`'s note that "every
   `rule_aspect` value measured worse" in earlier testing — measured worse
   is the right characterisation once reading order is controlled for, not
   an artifact of that earlier testing.

Taken together: no single value of either whole-component parameter is a
clean win — every direction trades one failure mode for another, because
the decision being tuned (keep the fused blob whole, or drop it whole) is
the wrong shape of decision for this input. This is exactly what the
research addendum predicted and is the reason it proposed pixel-level rule
removal instead of a component-level gate.

## Answering the assignment's classification (item 1)

Per-span classification for this page's losses, as far as traced:

- **Line never banded**: not observed. Band/fragment count (196) is close
  to truth line count (203), consistent with the prior audit's finding.
- **Component dropped by a filter**: `Observed` for the **International**
  and **Global** header blobs specifically (`furniture_fraction`'s `wide`
  test, default 0.2). Not observed as a *general* mechanism in the data
  cells — no cell-region component in the inspected rows approaches the
  furniture-scale threshold.
- **Merged into a rule component**: `Observed`, but the "rule" is the
  underline under section headers, not a table cell rule (there is no
  table-cell rule on this page). Confirmed for all five headers by
  connected-component measurement; two of the five fall under
  `furniture_fraction`'s default threshold and are *kept* as one
  glyphish-but-wrong blob rather than dropped — both are the same
  underlying fusion, differing only in which side of one threshold the
  resulting blob's width lands on.
- **Merged/touching at the individual-glyph level (not a rule)**:
  `Observed` in the data cells — digit+`$`, and comma marks, at this
  page's very small (9-10px x-height) type. This is the dominant mechanism
  in the numeric grid specifically, and is unrelated to any rule/furniture
  gate.
- **Misread (matcher noise)**: `Observed` throughout, both in touching-glyph
  fallout (`"3"→"5"`, the merged `0$`→`®`) and in otherwise-segmented small
  text — consistent with `filing__r000583`'s font-coverage finding, though
  this page's small size rather than an unrepresented style looks like the
  proximate driver here (not separately verified against a font-style
  hypothesis in this pass).
- **Reading-order only**: `Observed` to be real but modest —
  line-matched CER (37.154%) is 2.99pp below end-to-end CER (40.144%).
  Most of this page's error survives reading-order-independent scoring; it
  is not primarily a reading-order artifact, contrary to what the page's
  dominant `"\n"→" "` confusion (125 occurrences) might suggest in
  isolation. `Inferred`: at least part of that 125 is genuine
  row-major-cell-per-truth-line vs. visual-row-banding disagreement (the
  header row's numeric-column fragments are confirmed, by `--layout
  --no-decode`, to land in truth order left-to-right as separate
  same-baseline fragments — exactly the shape that produces a `\n`→`" "`
  mismatch for a correctly-segmented row), but the built-in line-matched
  metric shows this is not the majority of the page's error, so it was not
  pursued further as a distinct line-item in this report.

## What this implies

- The 2026-09-23 addendum's hypothesis ("dense tables: remove ruling
  pixels") is **wrong as literally stated for this page's data cells**
  (no rules exist there) but **right, and now directly evidenced, for the
  page's underlined section headers** — text-touching rule pixels really
  do fuse into one component there, and a whole-component accept/reject
  gate genuinely cannot resolve it cleanly (Finding 3). A pixel-level rule
  strip before component labelling (the addendum's proposed direction)
  would plausibly fix the header case without the collateral hyphen/minus
  damage `rule_aspect` demonstrably causes — but that is this report
  naming a candidate shape, not proposing constants or a rule; per
  `CLAUDE.md` and the addendum's own framing, that decision belongs to
  `ocrcer-architect`.
- Underlines are a distinct visual feature from table-cell ruling and
  worth naming separately: whatever fix targets "dense tables: remove
  ruling pixels" should be scoped (or explicitly extended) to cover
  underline rules beneath header/title text too, since that is where this
  page's evidence actually is, not in its numeric grid.
- The data-cell losses on this page are a different, already-catalogued
  problem: touching glyphs at very small type size (survey doc §4,
  drop-fall's target case) — a segmentation problem at the *glyph* level,
  unrelated to rules or furniture/aspect gates, and not something either
  tested parameter can address at any value without collateral damage.
- The built-in `line-matched CER` metric is doing real, useful work here
  and should probably be a standard second number reported alongside
  end-to-end CER on future dense-table pages, per the research addendum
  that proposed it — the gap it reveals (2.99pp on this page) is far
  smaller than a naive reading of the `"\n"→" "` confusion count would
  suggest, and prevented this report from mis-attributing this page's
  error to reading order.

## Proposed rule (shape only — constants and wording are the architect's call)

A pixel-level pass, before connected-component labelling, that identifies
and removes **long, thin, near-horizontal or near-vertical ink runs**
(table rules *and* underline strokes are the same geometric shape: high
aspect ratio, roughly constant thickness) from the binarised mask, subject
to a length floor tied to a measured, scale-free quantity on this project's
own model (the addendum's suggestion: the measured em-dash aspect bound
from `ocrcer-build aspect`, times the page's median component height) so
that no character stroke of plausible size is ever caught. Component
labelling then runs on the rule-stripped mask, so a header's letters and
its underline become separate components the way `Merchandise`'s digits and
`$` currently do *not*. This is a new stage (image-level, ahead of
`components::label`), not a change to `is_glyphish`, `furniture_fraction`
or `rule_aspect` — those three counterfactuals in Finding 3 show that
tuning the existing whole-component gate cannot get this page's headers
right without breaking something else the same gate also has to guard
(ordinary hyphens, minus signs, wide legitimate words). Whether the
stripped-pixel version needs to preserve *some* signal of "this row was
underlined" for anything downstream (there is nothing in the current
architecture that consumes that) is a question for `ocrcer-architect`, not
assumed here.

## Caveats

- Single page, per instructions — no claim here about this mechanism's
  share of the corpus-wide aggregate. The prior audit's 9.4%
  page-level attribution for `filing__r000022` (of the six-page worst-CER
  sample) is unaffected by this report except that its category label
  should now read "underline/header fusion + small-font touching glyphs,"
  not "narrow-column reading order," which this report finds essentially
  no evidence for as the primary mechanism (line-matched CER is only
  2.99pp below end-to-end).
- The ≈135-character/37-38% figure for header-fusion deletions is a
  length-differential estimate (`Inferred`), not a re-run alignment
  scoped to just those five lines — the precision claimed is "large and
  concentrated," not the exact number.
- No source code or model file was modified. `target/release` was left
  untouched; all counterfactuals and the rebuild used
  `CARGO_TARGET_DIR=target/runtime-diag`. `cargo test --workspace`
  (via the same isolated target dir) is green: 154 + 71 + 42 + 14 + 7 + 3
  + 2 + 2 passed, 0 failed, 11 ignored, across the workspace's crates.

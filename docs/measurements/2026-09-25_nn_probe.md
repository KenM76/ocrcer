# 2026-09-25: throwaway neural probe (chunk-15 pre-check)

Per `docs/ARCHITECTURE.md` §11, "Candidate: a throwaway neural probe before
chunk 15, on the extractor's own dumps." Branch `nn-probe`, not merged.
Every number below is **measured** (a script run, logged); none is fitted
into the model, and nothing here touches `model/out` in the main tree or
the score set (finfilings, finfilings-val, pages-cov, fixtures were never
read).

## Headline

**The prototype matcher still wins.** On the real-crop sample: matcher
92.37%, network-with-geometry 91.13%, network-no-geometry 86.76%
(char top-1, exact match). The 107-dim geometry features help the network
(+4.4pp over the no-geometry ablation) but do not close the gap to the
matcher already shipping in `model/out/ocrcer.ocrw`. This is a loss for the
probe's premise, stated as prominently as the win below.

**The win**: geometry features are clearly load-bearing for the network —
without them, punctuation collapses to 56% (vs 86% with geometry, vs 98%
for the matcher) and case pairs (`0/O/o`) do relatively better only because
the network without shape cues falls back on frequency priors. This
corroborates `CLAUDE.md`'s baseline-relative feature-group argument
independent of the matcher path.

## Method (how obtained)

- Rust: `crates/ocrcer-bench/src/bin/nn_dump.rs` (new bin, `nn-dump`,
  `ocrcer-bench`). Calls `ocrcer_core::feature::extract_with_grid` (new,
  small addition to `ocrcer-core/src/feature.rs`: shares its inner
  computation with the existing `extract()`, adds the 32x32 grid as a
  second return value) — the same extractor the bank build and the runtime
  matcher use. No feature computation happens in Python.
- Bank renders: `ocrcer_build::bank::{Fonts, Renderer}` against the
  54 shippable faces (`model/fonts.tsv`, `include_local_only=false`), all
  187 charset classes, sizes 16/20/24/32/48px, 4 deterministic-seeded
  variants each (0=clean, 1-3=seeded scan damage: sub-pixel shift, partial
  blur, additive noise, threshold jitter, 3x3 erode/dilate). Split
  80/20 train/val by a seeded hash of (class, face, size, variant), not by
  page or font family, so no leakage between the two.
  - `bank_train`: 160,099 rows. `bank_val`: 40,281 rows.
- Real crops: `D:/Dev/ExcludedPrivate/ocrcer/pages/finfilings-train`,
  gated on `bench/splits/manifest.tsv`'s `multifinben-englishocr` /
  `train` rows only (`splits::assert_fittable` re-checked per row; never
  finfilings, finfilings-val, or pages-cov). The manifest's 427 train rows
  are grouped by shard with an uneven shard-size distribution (shard 1
  alone holds 131/427); reading a prefix would have biased the sample
  toward one shard, so `nn-dump` took every 5th manifest row instead
  (`stride=5`), yielding **86 pages spread proportionally across all 8
  shards** (4/26/13/4/5/13/7/14 per shard) rather than the full 427 —
  a wall-time bound (measured ~18.5s/page under observed machine
  contention; full 427 pages projected ~2.5-3h), reported here rather than
  run silently. `page_stride: 5` is recorded in `summary.json`.
  - A word only contributes chars if OCRcer's own segmentation produced
    exactly the truth word's character count (same gate at the line
    level for word count). This is a **selection-bias filter that favours
    already-well-segmented text**, not a random sample of the real pages:
    - lines qualifying: 7,657 / 11,195 (68.4%)
    - words qualifying: 13,087 / 15,636 (83.7%)
    - chars dumped: 72,874; chars out of charset: 0; chars with a bad crop
      rect: 0
  - For each qualifying real char, `nn-dump` also runs
    `ocrcer_core::r#match::nearest(model, &raw, k=1, italic_ok=true)` using
    the fitted `model/out/ocrcer.ocrw` (rebuilt in this worktree before the
    dump), so the matcher and the two network variants are compared on
    **identical crops** with identical features.
- Python: `tools/nnprobe/train.py`. Computes nothing from pixels — loads
  the Rust-dumped `G`/`X`/`y` arrays and the matcher's own dumped `top1`
  column. Architecture per the §11 contract: conv3x3x16-relu-pool ->
  conv3x3x32-relu-pool -> dense(2048+107 -> 128)-relu -> dense(-> 187).
  Ablation: `no_geometry` drops the 107-dim concat at the dense head.
  `--wide` variant not run (not needed to answer the headline question).
  Seeded (`SEED=20260925` for Python/NumPy/PyTorch). Adam, lr=1e-3,
  batch 256, 12 epochs.

## Conclusion

The throwaway probe answers the question it was built to ask: on this
project's own charset, fonts, and real filing crops, a small CNN with the
extractor's 107-dim features concatenated in gets close to (but does not
beat) the already-shipping prototype matcher, and loses badly to it once
the geometry features are removed. Chunk 15 should not expect a free
accuracy win from replacing the matcher with a network of this size and
this training set; if a network is pursued it should be additive
(ensemble/fallback on low-confidence matcher decisions) rather than a
replacement, and geometry features are not optional input to it.

### Item 1 — was round 1 undertrained, or is ~85% a shared ceiling?

### Item 3 — fusion: this is a loss, reported as one

Extended `nn_dump.rs` to also emit the matcher's top-5 classes and
distances per real crop (`Sink5`, `real_topk_class.u16`, `real_topk_dist.f32`).
The "simple fusion" specified: fit an affine map from the network's
`-log softmax(p)` to the matcher's distance units via OLS on one fold's
test rows (`np.linalg.lstsq`), apply the mapped threshold to pick net vs.
matcher on the other fold's test rows.

| | scale_a | scale_b | fusion acc | net acc | matcher acc |
|---|---|---|---|---|---|
| fusion1 (scale fit on fold2 test = real-A, applied to fold1 test = real-B) | -0.2265 | 4.4072 | 0.9178 | 0.9755 | 0.9176 |
| fusion2 (scale fit on fold1 test = real-B, applied to fold2 test = real-A) | -1.3216 | 4.3454 | 0.9286 | 0.9752 | 0.9293 |
| mean | — | — | **0.9232** | **0.9753** | **0.9234** |

**The fusion does not work.** Fusion accuracy tracks the matcher's accuracy
almost exactly (0.9178 vs. 0.9176; 0.9286 vs. 0.9293) and is ~5.2 pp below
the network alone. `scale_a` fits **negative** in both directions, which is
the wrong sign: a larger `-log p` (a less-confident network prediction)
should map to a *larger* distance-equivalent (justifying more deference to
the matcher), not a smaller one. A negative slope means the fused threshold
inverts that relationship, and the fusion rule ends up deferring to the
matcher on the large majority of rows almost regardless of net confidence —
which is why the result tracks the matcher, not some useful blend. Per-group
evidence for this: on `lowercase` in fold1 the fusion is *below both*
standalone classifiers (11,674 correct vs. matcher's 11,709 and net's
11,898) — proof the naive scale-fit is occasionally worse than either input
alone, not just "matcher-shaped."

The oracle numbers explain why there is not much for a *better* fusion to
recover, and this is worth reading before concluding fusion is the right
next investment: `matcher_wrong_net_right_frac` is 6.34% (fold1) / 5.64%
(fold2) — the net rescues most of what the matcher gets wrong — but
`net_wrong_matcher_right_frac` is only 0.55% (fold1) / 1.04% (fold2): the
matcher only rarely gets right what the net gets wrong. Oracle-union
accuracy is 0.9810 / 0.9856, only ~0.5–1.0 pp above net alone (0.9755 /
0.9752). **Given real training data, the practical recommendation is to
prefer the network over this fusion scheme, not to invest further in this
particular linear-scale fusion** — the OLS-fit conversion as specified in
the task does not produce a useful decision rule, and a better one (e.g. a
constrained-positive-slope or isotonic calibration, or simply "trust net
unless its own confidence is very low") was out of scope for this round and
is left as an open item, not implemented and not claimed as working.

### Round 2 conclusion

Round 1's "matcher wins" verdict does not survive item 2: it was specific
to the renders-only training condition, and reverses (network +5.2 pp mean)
once real crops are added, which is what chunk 15 will actually do. Item 1

more promising than round 1 suggested, but only in the pure top-1 sense
measured here, on this selection-biased slice, without the fusion, gating,
or calibration machinery the matcher already has in production — none of
that is re-derived, re-scored, or a substitute for chunk 15's own gates.

| digits | 9,025 | 97.9% | 89.5% | 97.0% |
| l/1/I | 2,798 | 89.8% | 91.5% | 95.9% |
| lowercase | 13,302 | 96.9% | **87.1%** | 98.3% |
| uppercase | 1,467 | 93.3% | 87.0% | 90.5% |
| punctuation | 3,664 | 98.1% | 96.6% | 98.5% |

Adding real-A prototypes fixes the matcher's worst group by a wide margin —
0/O/o group accuracy 64.0% → 91.4%, driven almost entirely by the digit `0`
itself (53% own-class accuracy in round 2 → **98.3%**, matching net+realA
exactly) — but every other group gets *worse*, `lowercase` most of all
(−9.8pp fold1, −12.2pp fold2). The net gets the same `0`-class fix (item 4
below) with no comparable collateral damage elsewhere.

**Why, checked rather than assumed:** the first hypothesis — that
re-quantising ~87K combined rows over one shared per-column `max|v|/127`
scale corrupts the original 50,095 prototypes' precision — was tested
directly and **refuted**. A diagnostic build (`NN_PROBE_DIAG=1
NN_PROBE_DIAG_ONLY=1`, same bin) compared the per-column quantisation scale
and the original prototypes' round-trip error with vs. without the real-A
rows in the batch:

```
base_n=50095 n_rows=87469 max_col_scale base-only=0.124843 combined=0.124843
  mean_abs_err base-only=0.000000 combined=0.000506
base_n=50095 n_rows=85595 max_col_scale base-only=0.124843 combined=0.124843
  mean_abs_err base-only=0.000000 combined=0.000246
```

The max column scale is *identical* with or without the real-A rows (the
real crops never introduce a more extreme value than the bank already had),
and the extra round-trip error the original rows pick up from sharing a
scale with real-A (~0.0005 in standardised units, where each dimension has
unit-ish scale) is far too small to explain multi-point swings. **Ruled
out.**

The confusion tables point to the real mechanism instead: matcher+realA's
top confusions are dominated by ordinary letter-shape pairs unrelated to
0/O/o — `4`→`2` (n=344), `t`→`o` (141), `i`→`h` (120), `o`→`n` (119) in
fold1; `o`→`b` (429), `e`→`d` (335), `n`→`a` (268), `i`→`h` (254) in fold2 —
none of which appear in matcher-without-realA's top-10 at all. **Labelled
interpretation, not a re-measured fact:** the real-crop prototypes are
themselves noisier than clean renders (scan/segmentation artifacts,
imperfect crop boundaries), and a hard k=1 vote has no mechanism to
down-weight a bad neighbour — so the class with the most real examples
(digit `0`, n=6,881, the single most common character in the corpus) gets
fixed outright, while the added density measurably increases
false-nearest-neighbour risk broadly, hurting classes the round-2 matcher
already handled well. `net+realA` does not share this failure mode because
it is a discriminative classifier that fits decision boundaries over all
training rows rather than taking a hard 1-NN vote — architecture, not just
data, plausibly explains the gap. This is a **finding for chunk 15**, not
just a `nn_dump.rs` artifact: adding real-scan prototypes to the matcher
as-is (chunk 13's proposal) is not a free win at k=1; it would need either a
weighted/majority vote, per-source down-weighting, quality filtering of
crops, or restricting the addition to specifically weak classes (0/O/o)
rather than uniform addition across the charset.

Oracle complementarity (net+realA vs matcher+realA, fold1):
both-right 31,663 (89.2%), both-wrong 696 (2.0%), net-right/matcherA-wrong
2,921 (8.2%), matcherA-right/net-wrong 220 (0.6%) — oracle-union accuracy
98.0%, i.e. even the *lower* of the two classifiers is right on cases the
other misses often enough that a hypothetical oracle beats either alone by
~2 points. Not proposed as an implementable strategy here — just recorded
because item 1 asked for it.

### Item 2: leakage between folds (cluster-disjoint re-split)

Round 2's page-disjoint split was a random 43/43 partition of the 86 real
pages (`random.Random(seed=20260925)`); filings recur (same company, same
template, boilerplate reuse), so page-disjoint does not guarantee
document-disjoint. Clustered the 86 pages by the same method
`bench/splits/README.md`'s near-duplicate check uses (normalise, word
5-gram shingles, containment), applied pairwise within the 86-page set:
`tools/nnprobe/cluster_pages.py`, `CLUSTER_THRESHOLD = 0.3` (a stated
choice — the README's own "somewhat related" boundary — not the
firewall's stricter `0.0`, since this is a CV-fold-balancing problem, not a
train/score integrity firewall).

**Result: 3,655 pairs checked, 3 near-duplicate edges found, all in shard
s7** (`filing__s7__r000447`↔`r000729`, `r000488`↔`r000765`,
`r000690`↔`r000795`) — 83 clusters total (80 singletons + 3 pairs).
Checked directly against round 2's actual fold assignment: **all three
pairs were split across round 2's random folds** — confirmed leakage, not
a theoretical risk. Greedy cluster-aware rebalancing (largest clusters
first, always to the smaller fold) produced a 43/43 split by coincidence
(`tools/nnprobe/cluster_pages.py`'s deterministic bin-packing, no size
target was requested).

**Effect on the headline numbers: negligible.** Net+realA mean 97.65% vs.
round 2's 97.53% (+0.12pp); matcher(no-realA) mean 92.37% vs. round 2's
92.34% (+0.03pp). The leak was real but too small (6 of 86 pages, 3 pairs)
to have been inflating round 2's numbers in any way that matters — **round
2's verdict stands**, now on a demonstrably leakage-safe split.

### Item 3: the render-val 60.02% figure — verdict

Traced the call chain (`nn_dump.rs` → `ocrcer_core::r#match::nearest` →
`pipeline.rs`) and found a real harness/engine mismatch: `nn_dump.rs`'s
bank-val matcher call hardcoded `italic_ok = true` for every row, while the
real engine computes `italic_ok` per word from a measured slant estimate
(`pipeline.rs`'s `read_word`, false for upright text) and the shipped model
has `layout.italic_gating = 1` (on, `model/params.tsv`). Added a second
column, `bank_val_top1_italicfix.u16`, using `is_italic_style()` on each
row's own known rendering face style (exact for a bank render, since the
row's true style is known — unlike a real scanned word where slant must be
estimated) as the faithful `italic_ok`.

**Measured effect of the fix: negligible.** Old (hardcoded true): 60.02%.
Fixed (per-row style): 60.11% (+0.09pp; 1,103 / 40,281 predictions
differ). The italic-gating mismatch is real and now fixed in the harness,
but it explains almost none of the 60% figure.

**The actual explanation, isolated by splitting on damage variant** (each
bank-val row is one of 4 seeded render variants: 0 = clean, 1–3 = seeded
damage recipes):

| subset | n | old acc | fixed acc |
|---|---|---|---|
| clean (variant 0) | 9,908 | 99.83% | 99.83% |
| damaged (variant 1–3) | 30,373 | 47.04% | 47.16% |
| **all (reported 60.02%)** | 40,281 | 60.02% | 60.11% |

Damaged renders are 75% of the val set and score ~47%; clean renders score
99.8%. **Verdict: real finding, not a harness bug** (beyond the
now-fixed, ~0.1pp italic-gating mismatch) — the matcher is measurably
fragile to the seeded damage augmentation at this scale/variant mix, and
the 60% headline is an artifact of the val population being
three-quarters damaged, not of a broken call.

One open, unresolved discrepancy worth flagging rather than closing
quietly: the shipped bank's own build-time census
(`docs/measurements/2026-09-24_italic_gating.txt`) reports int8 top-1
accuracy **92.23%** (36,961/40,076) on its own held-out check — well below
this run's clean-subset 99.83%. The two figures measure different
populations (the build census is a LOOCV-style check over the actual
~50,095 shipped prototypes; this run's "clean" bank-val rows are a 20%
held-out slice of a much larger fresh render matrix — same faces/codepoints
but drawn independently per class/face/size/variant, so a held-out row's
same-face/class/size sibling at a different damage variant is very likely
still in `bank_train`, which not a true prototype-level LOOCV) — **labelled
as a plausible explanation, not verified further**; flagged for whoever
next touches the build census methodology rather than resolved here, since
resolving it is out of this round's scope.

### Item 4: 0/O/o breakdown, kept

Repeated for both new classifiers, concatenated across the cluster-disjoint
folds' test sides (every real-A row scored exactly once):

| classifier | `0` acc (n=6,881) | `O` acc (n=163) | `o` acc (n=2,471) |
|---|---|---|---|
| matcher+realA | 98.29% | 77.91% | **61.39%** |
| net+realA | 98.29% | 87.12% | 98.34% |

Matcher+realA fixes `0` completely (round 2's matcher-without-realA: 53.22%
own-class accuracy) but **craters `o`** (round 2 baseline: 94.37%) — exactly
the pattern item 1's "added real-`0` density hurts nearby classes"
interpretation predicts, since `0`, `O`, and lowercase `o` are the most
visually confusable triple in the charset and `0` is by far the
best-represented real-crop class. Net+realA fixes `0` to the same 98.29%
without the `o` collateral damage.

### Round 3 conclusion

The fair comparison (item 1) sharpens, rather than reverses, round 2's
verdict: net+realA (97.65%) still clearly beats matcher-without-realA
(92.37%), and now also beats matcher+realA (89.61%) — giving the matcher
the same real crops the net got does not close the gap, it widens it,
because a naive k=1 prototype addition is a net negative for the matcher
overall even though it fixes the specific weak group (0/O/o, via the digit
`0`) that motivated trying it. Item 2 confirms round 2's fold split had a
real, small leak (3 pairs / 86 pages) that moved the headline numbers by
less than 0.3pp either direction — round 2's numbers were not meaningfully
inflated. Item 3 resolves the "suspicious 60%" as a real finding (damage
fragility, three-quarters of the population is damaged) with a small,
separately-fixed harness bug (italic-gating hardcoded true, ~0.1pp) riding
along, not explaining it.

**For chunk 15:** this round strengthens the case for a net-based (or
net-assisted) path over matcher-alone, but item 1's result specifically
argues *against* chunk 13's "just append real-scan prototypes to the
matcher" as a free lunch — it is a measured net loss at k=1 without
additional machinery (weighting, filtering, or per-class targeting). None
of this is a substitute for chunk 15's own gates, calibration, or
production-path decoder integration, which nothing here re-derives.
